# Efforts and the backlog

The canonical groomed backlog is stored in `efforts/` on the `main` branch. Each effort
is in its own folder, and they can be nested, e.g.
`<parent-effort-slug>/<child-effort-slug>/<grandchild-effort-slug>`.

Each effort folder contains a file named `<EffortName>.md`, matching its slug
but in PascalCase.

## Frontmatter

Every effort file carries:

```yaml
---
slug: <slug>       # this effort's identity; matches its folder name; leaf of
                   # the slug chain (019f39dc-8ebf-7735-812d-522cc242a8b8.md)
parent: <slug>     # parent effort's slug; omitted for a top-level effort
status: <state>    # sub-state within open: planned | in-progress
---
```

Efforts carry no `gist:` — unlike kb docs, an effort's one-line summary is
derived from its `## Goal` section (see below), not stored in frontmatter.

## Goal

Every effort file has a `## Goal` section. Its first paragraph is the effort's
gist: a single sentence stating the outcome.
[`nosedive dump-backlog`](019f4a6c-136b-750a-8197-277b25f151f2.md) collapses that
paragraph to one line for its tree, so keep the first paragraph self-contained.

## Tracking

When new work is requested, it must go through the effort backlog.

Create an effort in `efforts/` before doing any other work. Fill out the
requirements, asking user for any missing information.

## Lifecycle

Presence under `efforts/` *is* openness: an effort exists there only while it is
open work. There is no `done` state to filter on — when an effort is finished it
**leaves** `efforts/` and its durable outcome lands in
[`kb`](00000000-0000-0000-0000-000000000000.md), either as a new document or as
an update to existing knowledge, depending on what the effort produced. The
`status:` frontmatter (e.g. `planned`, `in-progress`) is only a sub-state
*within* open — not started vs underway.

So the whole of `efforts/` is the live backlog; listing it
([`dump-backlog`](019f4a6c-136b-750a-8197-277b25f151f2.md)) needs no status
filter.

# Gates

A gate records a condition the work should satisfy and evaluates it with an
executable check. Humans and agents can run the same check and inspect the same
result instead of relying on memory or a reviewer's guess.

Gates follow the real system boundary: a gate may inspect more than one scoped
repository, and its relationship to a feat names when it runs (`land`, `test`,
or another supported action). A red or unwritten gate keeps the work from being
reported as complete.

Once work has landed, a `test` gate can survive it as a repeatable regression
check. If a gate goes red during
[`test`](./1e62a79d-4e06-552d-be5a-4c59c85f86bf.md), a `dive` will be
[minted](./e8909eff-aee5-54f2-9ce2-85c2582e39f0.md) to fix it.

When the active dive scopes the bridge, `land` and `test` read bridge gate
documents, declarations and scripts from its hydrated `__self` checkout.
Otherwise they read the live bridge. Gates added on the dive run; gates removed
from its declarations do not. The active dive's own links remain live
bookkeeping. Packaged gates continue to resolve from the package.

Land reports scripts that differ from the live bridge (including new scripts)
as `(changed on this dive)`, on passing and failing results alike. Gate source
must be committed in its owning checkout. No dive content is brought into the
live bridge until the gates pass and land reaches its existing bring-in step.

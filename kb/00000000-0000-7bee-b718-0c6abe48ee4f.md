# Knowledge Base

This directory is the single source of truth for reusable content.

It's a flat store of markdown documents. Each document is named `<quid>.md`
and is self-describing via YAML frontmatter. The `<quid>` is the document's
stable identity; human-readable identity lives in the frontmatter `name`.

This document is the store's schema: how a doc is shaped, named, linked and
scoped. What any particular kind of doc *means* lives in that kind's own doc,
listed under [Kinds](#kinds) below.

## Agent bootstrap

Before doing assigned work in this repo, search `kb/` for `kind: foundation`
and read every matched document in full.

```sh
rg -C3 "^kind: foundation" kb
```

Foundation docs are always read in full. For every other kb doc, the `gist:`
frontmatter line is an authoritative summary that may be acted on without
opening the doc body. Scan gists instead of opening docs for general context:

```sh
rg -N "^(name|gist):" kb/*.md
```

Open a non-foundation doc only for a specific detail its gist does not answer.
To resolve one term to its doc or docs, search by `name:`:

```sh
rg "^name: <term>" kb
```

## Memory policy

The kb is the shared memory. No agent stores project-specific knowledge in its
own private memory -- anything learned about this project (decisions,
conventions, gotchas, structure) goes into a kb document instead. Private
memory dies with the agent; the kb persists, so future agents and humans
benefit from what was learned. If knowledge is worth keeping, it is worth
writing here. If asked to remember something, store it in the kb.

## Frontmatter

Every document has at least:

```yaml
---
kind: <kind>         # the domain of knowledge this document falls under
id: <quid>           # matches the filename; see the quid convention below
name: <name>         # human identity: a leaf-first dot-joined chain of
                     # slugs (see Names below); unique within its kind;
                     # the grep target
gist: "<line>"       # the doc's cache line: one line that answers its most
                     # common lookup outright (see Gists below)
---
```

Frontmatter uses **KINGSMetaL** order: `kind`, `id`, `name`, `gist`, then
optional `scopes`, `meta`, and `links`. The order is canonical for readability
and grep ergonomics; parsers still treat frontmatter as key-addressed YAML.

Frontmatter must be valid YAML. Quote prose values, especially `gist`, because
cache lines often contain colons, quotes, backticks, or other punctuation that
plain YAML scalars can misread. Use 2-space indenting.

Frontmatter keys use kebab-case, never camelCase or snake_case.

## Kinds

Nosedive reads five kinds. Each is defined in its own doc, and that doc is the
reference for what the kind means:

- [feat](00000000-0000-7433-9095-caa4a7369645.md) -- a goal worth organizing
  work around.
- [dive](00000000-0000-749c-844b-2318117bffb0.md) -- one bounded, resumable
  attempt at a slice of a feat.
- [repo](00000000-0000-7a04-a8f4-6f75484220cb.md) -- one independently
  versioned implementation boundary.
- [gate](00000000-0000-76cb-a899-f8e90db8ca5c.md) -- a repeatable, executable
  check on the state of the work.
- [memo](00000000-0000-70fd-9a8c-5b0f34e248e2.md) -- durable information found
  by following a breadcrumb.

`kind: foundation` is the sixth: a document that defines the store itself --
its conventions, schema, and rules -- rather than reusable content. This
document is one.

A kb may hold any other kind its owners find useful. Nosedive neither defines
nor reads them, so this document does not describe them; they are the kb
owner's own vocabulary.

## The dive record and the active marker

A dive doc's frontmatter is shaped like:

```yaml
---
kind: dive
id: <quid>
name: <slug-chain>.<quid-last-6>
gist: "<line>"
scopes:
  - <repo-ref>
meta:
  feat: <feat-path>
  diver: <person-or-agent>
---
```

The body is the dive log: progress notes, handoff notes, artifacts, warnings,
repo heads, and any context the next human or agent needs.

The active workspace focus is the dive id in
`<nosedive-workspace>/.nosedive-ref`, which contains only:

```text
id: <dive-id>
```

That marker points to one `kind: dive` doc, and that doc is the single active
dive for the workspace. Other dive records can exist for the same feat; they
are not active in this workspace unless the marker points at them.

## Artifacts

Generated outputs that belong to kb docs live under `kb/artifacts/` as
quid-named files with whatever extension fits the artifact, for example
`kb/artifacts/<quid>.png` or `kb/artifacts/<quid>.md`. The owning kb doc links
to the artifact. If all links to an artifact are removed, the artifact may be
deleted manually; no garbage-collection machinery exists yet.

## Names

A doc's `name:` is a **leaf-first, dot-joined chain of slugs** -- the same
grammar as a feat's slug chain. The **leaf is the thing's natural name,
verbatim** (a single kebab-case token, no dots); ancestors qualify it when
the natural name is shared by several documented things (e.g.
`our-tools.mydivision` and `our-tools.otherdivision` for two repos that share
a name). Most docs are unambiguous and their name is just the leaf. Never
disambiguate by mangling the leaf itself (no `our-tools-mydivision`): that
breaks leaf-prefix lookup.

**Uniqueness is required on (`kind`, full name)** -- a full name must be
unique within its kind, but the same name may recur across kinds. When a
lookup matches several docs, `kind` and the gists disambiguate.

## Gists

A doc's `gist:` is its **cache line**: one line that answers the doc's most
common lookup outright -- exact formats, identifiers, and commands appear in
the gist literally, not paraphrased. Readers are entitled to act on a gist
without opening the body; the body carries rationale, edge cases, and history.

When writing or editing a doc, ask "what will someone most often come here to
get?" and put that, verbatim, in the gist. Keep it to one line -- a gist covers
the *most common* lookup, not everything the doc knows; overflow belongs in the
body.

Gist completeness is what makes selective reading safe: agents are instructed
to act on gists without opening bodies, so an incomplete gist yields a
confident wrong answer -- not extra reads.

## Links to related docs

When a kb doc references a concept that is itself defined by another kb doc,
link to that doc. Use a relative Markdown link to the related doc's quid
filename, not a `name:` link or an absolute path, for example
`[slug chain](019f39dc-8ebf-7735-812d-522cc242a8b8.md)`.

Do this for concepts that the reader may need to follow to understand or edit
the current doc. The prose can still use the human name, but the link makes the
relationship durable across renames and homonyms.

## Links

`links:` declares related kb documents that provide context for the current
doc. Each entry is exactly one of two forms, mirroring `scopes:` -- a repo-root
relative file path string, or a single-key map keyed by repo-root relative file
path carrying an optional metadata object:

```yaml
links:
  - kb/<quid>.md           # bare provenance link
  - kb/<quid>.md:          # file target + metadata object
      rel: <role>          # optional relationship/state
      anchor: <section>    # optional section anchor
```

- **Target path** -- the repo-root POSIX path of an actual file, either the
  whole string entry or the single key of the map. KB doc links use
  `kb/<quid>.md`; artifact links use paths such as `kb/artifacts/<quid>.mjs`.
  Do not use bare quids: frontmatter links should be followable as files.
- **`rel`** -- optional role the linked doc plays for this doc, an open string.
  A feat's links to its dives use it as the pickup-state signal; other kinds
  may define their own values.
- **`anchor`** -- optional Markdown-style section anchor. Advisory context, not
  a hard dependency; anchors may have drifted or be absent. An anchor is only
  valid in the map form: the older `<quid>#anchor` string form is no longer
  allowed.

Use `links:` when the relationship belongs in metadata. Use body links when the
prose itself depends on the reference.

Validation should treat `links:` as best effort: check that the referenced file
path exists when possible, but do not require anchors to resolve.

## Scopes

`scopes:` declares **where a doc's knowledge applies**, as a list of explicit
map entries:

```yaml
scopes:
  - .:
      render: gist
  - <repo-id>:
      path: <optional-repo-relative-path>
      ref: <optional-ref>
      mode: <optional ro|rw>
      render: <optional gist|body>
      flags:
        - <optional-extension-flag>
```

- **`<repo-id>` key** -- the `id` (quid) of a `kind: repo` doc. Every repo
  worked in has one, so the link is always available. Ids are stable across
  renames; never scope by name.
- **`.` key** -- reserved bridge/self scope key.
- **`path`** -- optional repo-root-relative directory; omitted means the repo
  root. The filesystem target resolves through the repo doc's `meta.path`.
- **`ref`** -- optional commit or ref. For gates, this is the last-known-good
  state proved for that repo. Other scoped docs normally omit it.
- **`mode`** -- optional repo access mode. `ro` marks the scope read-only; `rw`
  marks writable.
- **`render`** -- optional explicit render override: `body` or `gist`.
- **`flags`** -- optional list for non-render extension flags.

Hard cut: legacy string shorthand forms such as
`<repo-id>[/<path>][@<ref>][:<flag>[,<flag>...]]` are invalid for literal
`scopes:` entries.

Validation notes for `.` entries:

- allow `render` and optional `flags`
- reject `ref`, `mode`, and `path`
- reject scalar `- .` form

A doc scoped to several repos lists several entries -- there is no wildcard or
group scoping.

Scoping a doc to a subdirectory means its knowledge is *in addition to* the
repo-root docs -- subdir-scoped docs must not repeat repo-level content.

## Finding scoped docs for a repo

To find docs that apply to a repo, first identify the repo id. If no feat
context is available, find the `kind: repo` doc whose `meta.path` matches the
working checkout:

```sh
rg -n "^(kind: repo|id:|name:|gist:|  path:)" kb
```

Then scan docs whose `scopes:` include that repo id. A scope applies at the
repo root when the scope key matches the repo id and no `path` is set. It
applies below a subdirectory when the scope value sets `path`.

Read the matching gists first. Open the full body only when the gist indicates
the doc may affect the work. When editing files under a subdirectory, include
both repo-root scopes and scopes whose path is an ancestor of the edited path.

## Finding a canonical definition

Docs write a defined term as a placeholder token, e.g. `<slug-chain>`. To find
where it's defined, grep the kb for that name:

```sh
rg '^name: slug-chain' kb
```

This is a leaf-prefix match: it returns every doc whose name's **leaf** is the
token -- usually one doc, or a few when the natural name is a homonym or
recurs across kinds (the leaf is never mangled to dodge a collision; ancestors
disambiguate). Each candidate's `kind` and gist, which states its scope in the
first clause, normally suffice to pick the right one from the grep output
alone. (The `<quid>` naming above is itself defined this way:
`rg '^name: quid' kb`.)

### By quid

Hit a bare id whose meaning is unclear -- in a link, an `id:`, a log line, or
an artifact name? It **might** be a kb document: `id` equals the filename, so
check `kb/<quid>.md` first. If that file exists, that's the definition. If not,
the id names something else and the kb won't explain it; grep to find any doc
that references it, but expect that many ids have no kb entry at all:

```sh
rg <quid> kb
```

## Conventions

- **quid** -- `<quid>` means an id nosedive minted: a UUIDv7 whose leading 48
  bits are the instant of minting. See `rg '^name: quid' kb`.

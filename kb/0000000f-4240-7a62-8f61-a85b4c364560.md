# Knowledge Base

This directory is the single source of truth for reusable content.

It's a flat store of markdown documents. Each document is named `<uuid>.md`
and is self-describing via YAML frontmatter. The `<uuid>` is the document's
stable identity; human-readable identity lives in the frontmatter `name`.

## Agent bootstrap

Before doing assigned work in this repo, search `kb/` for `kind: foundation`
and read every matched document in full.

```sh
rg -C3 "^kind: foundation" kb
```

If `rg` is not available:

```sh
grep -r -C3 "^kind: foundation" kb/
```

Foundation docs are always read in full. For every other kb doc, the `gist:`
frontmatter line is an authoritative summary that may be acted on without
opening the doc body. Scan gists instead of opening docs for general context:

```sh
rg -N "^(name|gist):" kb/*.md
```

Open a non-foundation doc only for a specific detail its gist does not answer.
To resolve one term to its doc or docs, search by `name:`:

```sh
rg "^name: <term>" kb
```

## Memory policy

The kb is the shared memory. No agent stores project-specific knowledge in its
own private memory  anything learned about this project (decisions,
conventions, gotchas, structure) goes into a kb document instead. Private memory
dies with the agent; the kb persists, so future agents and humans benefit from
what was learned. If knowledge is worth keeping, it is worth writing here. If
asked to remember something, store it in the kb.

## Frontmatter

Every document has at least:

```yaml
---
kind: <kind>         # the domain of knowledge this document falls under
id: <uuid>           # matches the filename; see the uuid standard below
name: <name>         # human identity: a leaf-first dot-joined chain of
                     # slugs (see Names below); unique within its kind;
                     # the grep target
gist: "<line>"       # the doc's cache line: one line that answers its most
                     # common lookup outright (see Gists below)
---
```

Frontmatter uses **KINGSMetaL** order: `kind`, `id`, `name`, `gist`, then
optional `scopes`, `meta`, and `links`. The order is canonical for readability
and grep ergonomics; parsers still treat frontmatter as key-addressed YAML.

Frontmatter must be valid YAML. Quote prose values, especially `gist`, because
cache lines often contain colons, quotes, backticks, or other punctuation that
plain YAML scalars can misread. Use 2-space indenting.

Frontmatter keys use kebab-case, never camelCase or snake_case.

Docs that should be materialized into working locations also carry an
optional `scopes:` list (see Scopes below):

```yaml
scopes:
  - .:
      render: gist
  - <repo-id>:
      ref: <optional-ref>
      mode: <optional ro|rw>
      path: <optional-repo-relative-path>
      render: <optional gist|body>
      flags:
        - <optional-extension-flag>
```

Docs may also carry an optional `links:` list (see Links below) to name related
kb docs or artifacts. Each entry is a repo-root relative file path or a
single-key map keyed by that path:

```yaml
links:
  - kb/<uuid>.md
  - kb/<uuid>.md:
      rel: <optional-role>
      anchor: <optional-section>
```

### `kind: foundation`

A document that defines the store itself  its conventions, schema, and rules
rather than reusable content that gets installed or consumed. This document is
one. Agents read every `kind: foundation` doc before adding to or consuming the
kb (see [CLAUDE.md](../CLAUDE.md)). Default render is `body`.

### `kind: placeholder`

Defines a metasyntactic variable  a `<token>` that docs write in place of a
concrete value (e.g. `<slug-chain>`, `<uuid>`). This is the canonical place
that token is defined, so it isn't re-explained (and allowed to drift) in each
consumer. The `name` is the bare token (no angle brackets), which is what makes
[the grep below](#finding-a-canonical-definition) work. The body is the
definition.

### `kind: repo`

Catalogs one git repository: what it is and where it lives. The `name` leaf is
the slugified folder name. Adds a `meta:` block:

```yaml
meta:
  path: <nosedive-workspace>/<dirname>
                              # working checkout, relative to this repo's
                              # root; absolute (`~` literal, not expanded)
                              # only for repos outside <nosedive-workspace>.
                              # This is the repo's canonical nosedive target.
  url: https://example.com/org/repo
                              # optional human-facing repository URL. Store
                              # HTTPS web URLs here, not in remotes.cloud.
  base-branch: main            # optional; defaults to main when omitted.
                              # Used as the detached read-only head and as
                              # the fallback base for writable sessions.
  remotes:                    # durable and bootstrap sources; cloud/local are
                              # optional, but at least one is required.
    cloud: git@example.com:org/repo.git
                              # durable upstream SSH clone/push URL; preferred
                              # source for nosedive-managed caches and
                              # persisted work.
    local: <path>             # optional existing local checkout/cache used
                              # only as a seed/provenance hint, not as the
                              # workspace hydration target.
```

Nosedive workspace hydration must create worktrees from a nosedive-managed
cache such as `.nosedive/cache/<repo-id>`, not directly from
`meta.remotes.local`. `meta.path` names the workspace target;
`meta.url` is the human-facing HTTPS repository page, and `meta.remotes.*` name
sources for preparing managed git state. Historical docs or command fixtures
may contain `meta.worktree-path`; treat it as a deprecated compatibility alias
only, and do not add it to new repo docs. When both `cloud` and `local` exist,
`cloud` is authoritative for durable fetch/push identity and `local` is only a
bootstrap convenience.

The repo doc body is the kb's clean summary of everything durable we know about
that repo: what it is, where it lives, how it is commonly worked on, and which
kb docs matter when touching it. Link to relevant memos, conventions, runbooks,
decisions, assertions, domain docs, and other scoped knowledge rather than
duplicating their bodies. When the implementation repository has a README, link
to it through the expected `meta.path` workspace location, for example
`[README](../<nosedive-workspace>/<dirname>/README.md)` or the appropriate path
implied by `meta.path`.

Do not import README contents verbatim into repo docs, and do not treat repo
docs as canonical README source. The README belongs to the implementation repo
and may legitimately use relative asset links, package badges, screenshots, or
other repo-local references. The repo doc should summarize or point at that
material only when it is useful kb knowledge.

A repo doc is a workspace-setup input -- its existence alone does not cause
anything to be generated, and repo docs are never rendered or materialized as
working-location documents. Working locations may contain marker files (for
example `.nosedive-ref`) that reference repo or dive ids; those markers are
references, not rendered repo-doc content. Updating a repo README is ordinary
implementation documentation work, separate from maintaining the kb repo
summary.

### `kind: domain`

Catalogs one owned DNS domain: registrar, authoritative DNS host,
nameservers, mail host, management URLs, and pointers to any repo-local source
of truth. Domain docs are for cross-project control-plane facts rather than
per-service DNS records.

The `name` is the lowercase domain name itself, including dots, e.g.
`sycdan.com`. This is the only kind whose `name` intentionally uses DNS label
dots instead of a dot-joined slug chain.

Domain docs may add a `meta:` block:

```yaml
meta:
  domain: sycdan.com
  registrar: dreamhost
  dns-host: freedns-afraid
  nameservers:
    - ns1.afraid.org
  registrar-management-url: https://example.com
  dns-management-url: https://example.com
  mail-host: mxroute
```

### `kind: convention`

Rules for working in particular repos or directories  code style, build/test
commands, how to spin up the app, gotchas. Carries `scopes:` pointing at the
repo(s)/dir(s) the rules govern. Default render is `gist`.

### `kind: skill`

A capability doc: procedural knowledge an agent should pull in on demand rather
than carry everywhere (the gist states likely triggers). Carries `scopes:` where
applicable. Default render is `gist`. Skill gists should start with an explicit
trigger such as `Read when ...` and include likely lookup keywords. Do not
compress the procedure into the gist; the gist should make the agent open the
skill body, not replace it.

### `kind: runbook`

A runbook doc describes a reusable operation or sequence of operations a
developer may ask an agent to perform. Runbooks are verby capabilities; the body
should include the procedure, commands, caveats, and verification steps needed
to perform the runbook. The `gist` names what the runbook accomplishes.

Runbook docs carry `scopes:`. A reserved `.` scope key means the bridge
itself, so the runbook is always included in bridge agent instructions
regardless of the current effort. Other scopes follow the ordinary repo-id
scope rules. Default render is `gist`.

Generated agent instructions include runbook names and gists. If the user asks
what runbooks are available or what they can do, answer with the preloaded
runbook names and gists. If a user asks to do something that sounds like a
runbook, open the full runbook doc to learn the procedure, then do it.

### `kind: dive`

One durable attempt on an effort. A dive records progress, repo scopes, branch
state, logs, artifacts, and `meta.diver`. The active workspace focus is
selected by `<nosedive-workspace>/.nosedive-ref`, not by legacy `.nosediverc`
`current.*` keys.

### `kind: assertion`

A durable, retestable behavior contract promoted from an effort expectation.
Assertions capture Given/When/Then-style facts that future work must preserve,
plus enough recreate information to find or rerun the executable proof in the
implementation repo. Carries `scopes:` when it applies to one or more repos.
Default render is `gist`.

Assertion metadata is for selection and history, not for storing the proof
command. When an assertion is tied to executable proof, use:

```yaml
scopes:
  - kb/019f514e-d8d5-7bc1-bf3f-d8e5092c6596.md:
      ref: <last-good-sha>
      mode: ro
meta:
  group: unit
  timeout-seconds: 5
```

`group` is a scheduling label such as `unit`, `smoke`, or `flow`; it is not a
closed vocabulary. The only special expectation is that `unit` assertions are
fast and runnable without extra infrastructure or network calls.
`timeout-seconds` is optional and defaults to `30`. Assertion scopes may carry
`ref` to record the last-known-good commit or ref for that repo. `mode: ro`
tells assertion runners to mount or check out that scope read-only unless the
proof explicitly requires writes.

Use the body for the contract and executable proof recipe. `## Given`,
`## When`, and `## Then` sections carry human-readable prose and may also carry
fenced bash blocks tagged `assertion-given`, `assertion-when`, and
`assertion-then`. Assertions are proof obligations, not optional notes and not
a promise that one universal runner command exists. Run each touched assertion
with the machinery indicated by that assertion or by the effort proof artifact
that links to it: a repo test command, smoke script, manual recreate recipe, or
tagged assertion blocks when a runner exists for them. If no executable proof
machinery is available, record that limit explicitly instead of treating the
assertion as satisfied. Scripts should invoke the real tool or test command
they are proving.

````md
# Resume from dive ref

## Given

A bridge kb has a `kind: dive` doc with
`effort: <effort-path>`.

```bash assertion-given
work="$(mktemp -d)"
trap 'rm -rf "$work"' EXIT
cd "$work"
# create bridge fixture
```

## When

Follow the workon runbook to select the dive and hydrate the workspace.

```bash assertion-when
npx -y nosedive@dev dump-backlog >/dev/null
# future deterministic tool invocation for selecting and hydrating "$dive_ref"
```

## Then

Nosedive reads the effort from the dive record and does not require the user
to pass an effort path separately.

```bash assertion-then
test -d workspace
```
````

When working in a repo, scan scoped assertion gists before finishing. If a
change touches asserted behavior, rerun the assertion proof. When the proof
passes on newer commits, update the assertion scope refs to the new tested
state. If the asserted behavior intentionally changes, update the assertion
gist, body, executable proof blocks, scopes, and metadata in the same work.

### `kind: decision`

A durable design decision record: context, options considered, the chosen
direction, consequences, and links to the foundation rules or related concepts
the decision interprets. Decisions are for "why this shape" knowledge rather
than active procedure. They may carry `scopes:` when the decision should be
surfaced while working in particular repos or directories. Default render is
`gist`.

### `kind: memo`

A piece of durable information meant to be found by following an explicit
breadcrumb, not by automatic agent-instruction materialization or broad gist
scans. Memos are for provenance notes, local-state explanations, and other
context whose audience starts from a pointer such as a kb id in
`.git/info/exclude`.

Memos may carry `scopes:` to declare which repos or paths the memo applies to.
Scoped memos are still lookup breadcrumbs, not automatic instruction content:
they have no default render and are not rendered into generated agent files
unless a later foundation rule explicitly gives memos a render behavior.

Commands may also use memos for durable failure explanations. A command throws
the memo UUID; the CLI resolves it into `nosedive-error: <gist>` and a command
that renders the full memo. Command docs link each such memo with `rel: throws`:

```yaml
links:
  - kb/<memo-uuid>.md:
      rel: throws
```

The memo links back to the command with `rel: thrown-by`. Every `rel: throws`
target on a command must be a `kind: memo` doc, and the two links must agree.

## Artifacts

Generated outputs that belong to kb docs live under `kb/artifacts/` as
uuid-named files with whatever extension fits the artifact, for example
`kb/artifacts/<uuid>.png` or `kb/artifacts/<uuid>.md`. The owning kb doc links
to the artifact. If all links to an artifact are removed, the artifact may be
deleted manually; no garbage-collection machinery exists yet.

## Names

A doc's `name:` is a **leaf-first, dot-joined chain of slugs**  the same
grammar as an effort's slug chain. The **leaf is the thing's natural name,
verbatim** (a single kebab-case token, no dots); ancestors qualify it when
the natural name is shared by several documented things (e.g.
`our-tools.mydivision` and `our-tools.otherdivision` for two repos
that share a name). Most docs are unambiguous and their name is just the
leaf. Never disambiguate by mangling the leaf itself (no
`our-tools-mydivision`): that breaks leaf-prefix lookup.

`kind: domain` docs are the exception: their `name:` is the lowercase DNS
domain itself, including dots, e.g. `sycdan.com`.

**Uniqueness is required on (`kind`, full name)**  a full name must be
unique within its kind, but the same name may recur across kinds (a
`repo` named `scripts` and a `runbook` named `scripts` can coexist). When
a lookup matches several docs, `kind` and the gists disambiguate.

## Gists

A doc's `gist:` is its **cache line**: one line that answers the doc's most
common lookup outright  exact formats, identifiers, and commands appear in
the gist literally, not paraphrased. Readers are entitled to act on a gist
without opening the body; the body carries rationale, edge cases, and
history.

When writing or editing a doc, ask "what will someone most often come here
to get?" and put that, verbatim, in the gist. Keep it to one line  a gist
covers the *most common* lookup, not everything the doc knows; overflow
belongs in the body.

Gist completeness is what makes selective reading safe: agents are
instructed to act on gists without opening bodies, so an incomplete gist
yields a confident wrong answer  not extra reads.

`kind: skill` gists are the exception: their job is to state when to read the
skill, not to summarize the procedure. Put procedure, commands, caveats, and
verification steps in the skill body.

## Links to related docs

When a kb doc references a concept that is itself defined by another kb doc,
link to that doc. Use a relative Markdown link to the related doc's uuid
filename, not a `name:` link or an absolute path, for example
`[slug chain](019f39dc-8ebf-7735-812d-522cc242a8b8.md)`.

Do this for concepts that the reader may need to follow to understand or edit
the current doc: foundation rules, placeholders, runbooks, conventions, memos,
repo docs, and design decisions captured in kb. The prose can still use the
human name, but the link makes the relationship durable across renames and
homonyms.

## Links

`links:` declares related kb documents that provide context for the current
doc. Each entry is exactly one of two forms, mirroring `scopes:` -- a repo-root
relative file path string, or a single-key map keyed by repo-root relative file
path carrying an optional metadata object:

```yaml
links:
  - kb/<uuid>.md           # bare provenance link
  - kb/<uuid>.md:          # file target + metadata object
      rel: <role>          # optional relationship/state
      anchor: <section>    # optional section anchor
```

- **Target path** -- the repo-root POSIX path of an actual file, either the
  whole string entry or the single key of the map. KB doc links use
  `kb/<uuid>.md`; artifact links use paths such as `kb/artifacts/<uuid>.mjs`.
  Do not use bare UUIDs: frontmatter links should be followable as files.
- **`rel`** -- optional role the linked doc plays for this doc, an open string.
  Effort dive links use it as the pickup-state signal (`pending`, `working`,
  `reviewing`; absent means plain provenance). Other kinds may define their own
  values.
- **`anchor`** -- optional Markdown-style section anchor. Advisory context, not
  a hard dependency; anchors may have drifted or be absent. An anchor is only
  valid in the map form: the older `<uuid>#anchor` string form is no longer
  allowed.

Use `links:` when the relationship belongs in metadata: a decision interpreting
a foundation section, a convention relying on a runbook, or a memo explaining a
local artifact. Use body links when the prose itself depends on the reference.

Validation should treat `links:` as best effort: check that the referenced file
path exists when possible, but do not require anchors to resolve.

## Scopes

`scopes:` declares **where a doc's knowledge applies**, as a list of explicit
map entries:

```yaml
scopes:
  - .:
      render: gist
  - <repo-id>:
      path: <optional-repo-relative-path>
      ref: <optional-ref>
      mode: <optional ro|rw>
      render: <optional gist|body>
      flags:
        - <optional-extension-flag>
```

- **`<repo-id>` key**  the `id` (uuid) of a `kind: repo` doc. Every repo worked
  in has one, so the link is always available. Ids are stable across renames;
  never scope by name.
- **`.` key**  reserved bridge/self scope key, primarily for bridge-scoped
  runbooks.
- **`path`**  optional repo-root-relative directory; omitted means the repo
  root. The filesystem target resolves through the repo doc's `meta.path`.
- **`ref`**  optional commit or ref. For assertions, this is the
  last-known-good state proved for that repo. Other scoped docs normally omit
  it.
- **`mode`**  optional repo access mode. `ro` marks the scope read-only;
  `rw` marks writable.
- **`render`**  optional explicit render override: `body` or `gist`.
- **`flags`**  optional list for non-render extension flags.

Render defaults come from `kind`: foundation renders as `body`; convention,
skill, runbook, assertion, and decision render as `gist`. `kind: memo` has no
default render; memo scopes are applicability metadata.

Hard cut: legacy string shorthand forms such as
`<repo-id>[/<path>][@<ref>][:<flag>[,<flag>...]]` are invalid for literal
`scopes:` entries.

Validation notes for `.` entries:

- allow `render` and optional `flags`
- reject `ref`, `mode`, and `path`
- reject scalar `- .` form

Tooling materializes scoped docs into agent instruction files at the resolved
locations during workspace setup (see the `kb-scoped-harness-docs` effort
while it is open). A doc scoped to several repos lists several entries
there is no wildcard or group scoping. Docs without `scopes:` are never
materialized.

Scoping a doc to a subdirectory means its knowledge is *in addition to* the
repo-root docs  subdir-scoped docs must not repeat repo-level content.

## Finding Scoped Docs For A Repo

To find assertion, convention, skill, runbook, memo, or decision docs that apply
to a repo, first identify the repo id. Prefer generated `CLAUDE.md` /
`AGENTS.md` frontmatter when present; repo/subdir instruction files should name
`repo-id` and `scope-path`. If generated frontmatter is unavailable, use the
current effort's `repos:` list. If no effort context is available, find the
`kind: repo` doc whose `meta.path` matches the working checkout:

```sh
rg -n "^(kind: repo|id:|name:|gist:|  path:)" kb
```

Then scan docs whose `scopes:` include that repo id. A scope applies at the repo
root when the scope key matches the repo id and no `path` is set. It applies
below a subdirectory when the scope value sets `path`. For a specific repo id:

```sh
rg -n -C4 "^(kind: assertion|kind: convention|kind: skill|kind: runbook|kind: memo|kind: decision|name:|gist:|scopes:|  - <repo-id>:|      path:)" kb
```

Read the matching gists first. Open the full body only when the gist indicates
the doc may affect the work or when the proof/recreate details are needed.
When editing files under a subdirectory, include both repo-root scopes and
scopes whose path is an ancestor of the edited path.

## Finding a canonical definition

Docs write a defined term as a placeholder token, e.g. `<slug-chain>`. To find
where it's defined, grep the kb for that name:

```sh
rg '^name: slug-chain' kb
```

If `rg` is not available:

```sh
grep -r "^name: slug-chain" kb
```

This is a leaf-prefix match: it returns every doc whose name's **leaf** is
the token  usually one doc, or a few when the natural name is a homonym
or recurs across kinds (the leaf is never mangled to dodge a collision
ancestors disambiguate). Each candidate's `kind` and gist, which states
its scope in the first clause, normally suffice to pick the right one
from the grep output alone. (The `<uuid>` naming above is itself defined
this way: `rg '^name: uuid' kb`.)

### By uuid

Hit a bare uuid whose meaning is unclear  in a link, an `id:`, a log line, or
an artifact name? It **might** be a kb document: `id` equals the
filename, so check `kb/<uuid>.md` first. If that file exists, that's the
definition. If not, the uuid names something else and the kb won't explain it;
grep to find any doc that references it, but expect that many uuids have no kb
entry at all:

```sh
rg <uuid> kb
```

## Conventions

- **uuid**  `<uuid>` means a UUIDv7 minted with a tool; see
  `rg '^name: uuid' kb`.

# Feats

A feat is an open unit of work represented by one `kind: feat` document in
`kb/`. The generated backlog memo renders those documents; it is not a
directory structure. The document's stable UUID is its identity and its `name`
is a leaf-first kebab-case slug chain for people to read and resolve.

A feat can be nested. A child and its parent each name the other in `links:`:
the child uses `rel: parent` and the parent uses `rel: child`. Nesting belongs
in those links, not in a filesystem path.

## Creating feats

Use `npx -y nosedive@dev pitch` to create a new feat:

```sh
npx -y nosedive@dev pitch "<gist>" [--name <slug>] [--parent <feat>]
```

`<gist>` is the concise statement of the work and is required. `--name` sets
the feat's leaf kebab-case slug; when omitted, nosedive generates a temporary
name. `--parent` accepts a feat UUID, a bridge-root KB path, or an exact
feat name. It writes the reciprocal parent and child links and derives the
new feat name from that parent.

Pitch creates the KB document for review. Add framing, scope, and implementation
notes to its body as the work becomes understood.

## Frontmatter and scope

Every feat has at least this identity:

```yaml
---
kind: feat
id: <uuid>
name: <leaf-first-slug-chain>
gist: "<concise description>"
---
```

Work that reads or changes repositories declares them in `scopes:`. Each scope
uses a repository KB doc UUID, optionally with a resolved ref and a mode:

```yaml
scopes:
  - <repo-id>:
      ref: <commit-or-ref>
      mode: rw
  - <reference-repo-id>:
      mode: ro
```

`rw` scopes may receive implementation changes; `ro` scopes are context only.
Dives inherit their feat's scopes, pinning the repositories that their
iteration needs. Repository docs record each repository's conventions, branch
practice, loads, and quality gates.

## Assertions and proof

A feat body may state the behavior it intends to establish. Durable,
testable behavior is recorded as a `kind: assertion` KB document scoped to the
repositories it concerns. An assertion links its executable prover artifact
with `rel: prover` and may record the exact commits a proof accessed.

Run an assertion with:

```sh
npx -y nosedive@dev prove <assertion-ref>
```

Use `--record` only when the prover and its scoped repositories are clean and
the proof should update the assertion's recorded input commits. Implementation
tests remain in their owning repositories; an assertion preserves the concise,
re-runnable cross-repo contract.

## Working a feat

Before implementation, read the feat, its parent context, its scopes, and
the applicable scoped assertions. Plan the repository tests and assertion proof
that cover behavior affected by the change. Run the repositories' documented
gates and relevant proofs before reporting the work complete, recording any
proof that could not run and why.

Use a dive for one concrete iteration. A `kind: dive` document is owned by its
feat and records the assigned diver, pinned scopes, implementation brief, and
handoff summary. The dive is the unit that `into`, `jump`, `bail`, `pack`, and
`land` operate on.

## Lifecycle

A feat is open while its `kind: feat` document appears in the bridge KB and
the generated backlog memo includes it. The feat body and its linked dives
are its working record. When its intended outcome has been delivered, retain
the document as durable context and preserve assertions, decisions, conventions,
or memos that future work needs.

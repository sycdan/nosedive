# Efforts and the backlog

The canonical groomed backlog is stored in `backlog/` on the bridge main
branch. Each effort is in its own folder, and efforts can be nested, e.g.
`<parent-effort-slug>/<child-effort-slug>/<grandchild-effort-slug>`.
Backlog directories without a matching PascalCase effort file are **domain
directories**: namespaces for project or owner grouping, not open efforts.

Each effort folder contains a file named `<EffortName>.md`, matching its slug
but in PascalCase.

An effort's **slug is its folder name**. Identity and nesting live in the
directory tree, not in frontmatter. The slug is the leaf of the
[slug chain](019f39dc-8ebf-7735-812d-522cc242a8b8.md).

A domain directory contributes to descendant effort slug chains even though it
is not an effort and has no phase. For example,
`backlog/gogglebox/auth-refactor/AuthRefactor.md` is the effort
`auth-refactor.gogglebox`; `gogglebox/` itself is only a domain row in backlog
output.

## Creating efforts

Use `npx -y nosedive@dev pitch` to create new efforts:

```sh
npx -y nosedive@dev pitch <slug> [--gist "<gist>"] [--pitch "<pitch>"]
npx -y nosedive@dev pitch <slug> [--gist "<gist>"] [--pitch "<pitch>"] --parent <effort>
```

`<slug>` is the new effort's kebab-case directory name. `--gist` sets the
frontmatter cache line. `--pitch` sets the initial `## Framing` body text. When
one is omitted, nosedive uses the other; when both are omitted, it derives a
simple title from the slug.

`<effort>` may be either a concrete backlog path such as
`backlog/parent-effort/ParentEffort.md` or a leaf-first effort slug chain such
as `parent-effort` or `child-effort.parent-effort`. Nosedive resolves the parent
to an effort directory, creates a subdirectory and PascalCase effort file from
the explicit slug, and leaves the new effort file in the working tree for the
developer to review, commit, and push when ready.

## Frontmatter

Every effort file carries, at minimum:

```yaml
---
phase: <phase>     # framing | shaping | building | testing
gist: "<line>"     # minimum prosaic description of the effort; typically
                   # derived from (or literally) the initial idea pitch
---
```

Effort frontmatter is valid YAML; quote prose values such as `gist`.

Efforts that work in repos also declare them:

```yaml
repos:
  - <repo-id>         # writable, uses repo doc base branch
  - <repo-id>@<ref>   # writable, overrides branch/ref for this effort
  - <repo-id>:ro      # read-only for this effort
  - <repo-id>@<ref>:ro
```

Format is `<repo-id>[@ref][:flags]`, where `@ref` and `:flags` are optional.
The only supported flag today is `ro`.

Workspace setup clones the listed repos and marks `:ro` ones read-only for the
duration of the effort.

## Phases

Efforts move through Shape Up-inspired phases, in order:

- **framing**  the idea exists as a pitch; the `gist` captures it.
- **shaping**  defining technical specs and expectations, spotting rabbit
  holes, marking out-of-bounds areas, goals, and nongoals.
- **building**  actual implementation, using TDD where practical; may spawn
  subefforts.
- **testing**  verifying the built thing does what was shaped.

A new effort starts at `phase: framing` with its gist. The body grows as the
effort advances: framing notes, then shaping output, then build/test notes.

## Expectations

Efforts that define testable behavior carry a `## Expectations` section before
or during shaping. Expectations are written as short Given/When/Then-style
contracts, not implementation notes. They describe what must become true from
the user's or system's point of view.

During building, use TDD where practical: turn each expectation into a failing
test in the implementation repo, make it pass, then write a proof document
under the effort directory's `.artifacts/`. Link that proof from the
expectation. Use the effort's `repos:` list to identify which implementation
repo or repos own the proof.

Expectation proof links live in the effort while the work is open:

```md
## Expectations

### Resume from dive

Given a bridge has a dive record for an effort
When the workon runbook selects that dive for the workspace
Then deterministic nosedive tools hydrate the workspace from the selected dive
record

Proof: [.artifacts/resume-from-dive.md](.artifacts/resume-from-dive.md)
```

Proof documents carry frontmatter naming the proving command and complete repo
state. `repo-commits:` maps every involved repo id to the exact commit sha that
was tested:

```yaml
---
expectation: resume-from-dive
command: "npm test"
repo-commits:
  019f514e-d8d5-7bc1-bf3f-d8e5092c6596: <sha>
---
```

The proof body names the relevant test path, test case, setup notes, output
summary, and any limits on what was proven.

When an effort leaves `backlog/`, durable expectations that future work must
preserve move to `kb/` as `kind: assertion` docs. The implementation repo keeps
the executable test; the kb assertion keeps the concise recreate-on-demand
contract and links to the relevant command or test.

An effort may leave `backlog/` only when every expectation is resolved. A
resolved expectation is one of:

- linked to a proof document under the effort's `.artifacts/` directory, and
  that proof document records a passing command plus complete `repo-commits:`
  state
- explicitly moved to a follow-up effort that remains in `backlog/`
- removed from scope with a short rationale in the effort body

Before removing an effort from `backlog/`, rerun or inspect the linked proof
commands for all covered expectations and promote durable behavior contracts to
`kind: assertion` docs only when they should outlive the effort.

## Implementation discipline

Before coding for an effort, read its `## Expectations` section and use the kb
foundation doc's scoped-doc lookup recipe to scan scoped `kind: assertion`
gists for the implementation repos named in `repos:`. If the change could
affect an expectation or assertion, plan the corresponding test or proof before
editing.

An agent must not mark an expectation done, move an effort out of `backlog/`,
or report implementation complete without either running the relevant proof
command or explicitly recording why it could not be run. Generic repo gates are
still required when the repo convention names them, but they do not replace
expectation-specific proof commands for touched behavior.

Before finishing an implementation turn:

- run the repo's normal gate and any expectation/assertion proofs touched by
  the change
- create or update linked `.artifacts/` proof docs for newly proven
  expectations, including `repo-commits:` for the exact commits tested
- update any durable `kind: assertion` docs whose behavior, executable proof
  blocks, scheduling metadata, or proven repo commits changed
- report which commands ran, which proof docs changed, and which assertion docs
  changed

## Tracking

When new work is requested, it must go through the effort backlog. Create an
effort in `backlog/` before doing implementation work. Fill out the requirements,
asking the user for any missing information when the request does not include
enough to pitch the effort safely.

Routine kb maintenance is not implementation work. When a user asks an agent to
remember something, clarify a foundation rule, or add a reusable note directly
to `kb/`, make the kb edit in place without creating a backlog effort unless
the kb change is part of a larger implementation effort.

## Lifecycle

Presence under `backlog/` is openness: an effort exists there only while it is
open work. There is no `done` phase to filter on. Domain directories may remain
under `backlog/` as empty or grouping namespaces because they are not efforts.
When an effort is finished it leaves `backlog/`; durable outcomes land in `kb/`
only when they are worth preserving as reusable knowledge, assertions,
decisions, conventions, runbooks, or memos.

So the whole of `backlog/` is the current backlog; listing it needs no phase
filter.

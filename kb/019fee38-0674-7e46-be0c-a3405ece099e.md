# Seed Refuses Level Downgrade

## Why

`.nosedive/config.yaml` is checked in and team-shared, and its
`compatibility-level` is what every other command reads to decide whether it can
read the bridge's data at all. `seed` writes that line on every run.

If the bridge already carries a level higher than the running package's, someone
has seeded it with a newer nosedive. Writing the lower level back would be a
downgrade of shared, checked-in state -- and would then make the newer
package refuse every command and demand a migration the bridge has already had.

`npx` makes the package version invisible, so nobody has to do anything wrong
for this to happen: one stale cache is enough. `seed` refuses instead, and names
both levels so it is obvious which side is behind.

## What to do

Upgrade the package, not the config.

- If you invoke nosedive through `npx -y nosedive@<version>`, the version is
  pinned in your agent instructions file. Take the version your teammate is on
  and re-run `seed` with it.
- If you invoke a plain `npx nosedive`, clear the stale entry
  (`npx clear-npx-cache`, or `npm cache clean --force`) and re-run.
- If you invoke a local checkout, pull and rebuild it.

Do not hand-edit `compatibility-level` downward. The number records what shape
the bridge's data is in; lowering it does not change the data, it only lies
about it.

# Level 3 domain model

The model level 3 implements. Written to be read on its own: an agent holding
this doc and the code needs nothing else to work a level 3 dive.

Level 3 is reserved by [the level doc](019ff102-cafa-780d-80bd-efb9c68617fc.md),
which stated the release boundary before the model existed. Where that doc's
earlier sketch and this memo disagree, this memo is current.

## Ship

A ship is an ordered chain of decks. It is a `kind: ship` doc, and
`.nosedive/config.yaml` lists ships by id:

```yaml
ships:
  - <ship-quid>
```

The ship doc carries the chain in `meta.decks`, entry deck first:

```yaml
meta:
  decks:
    - <entry-deck-quid>
    - <final-deck-quid>
```

Array position is the order. `drop` advances a feat to index+1 and `lift`
retreats it to index-1. Position is the only ordering; a deck never links its
neighbours, because ordering is orchestration rather than knowledge. That is
what stops an agent reading the `production` deck from conflating its feats with
`uat`.

A deck belongs to exactly one ship. Nothing in a deck doc records this, so it is
validated by scanning every ship in `ships:` -- enforced in the bridge pre-push
hook.

Config stays a flat map: `ships:` is a plain array of ids, and the nesting lives
in the ship doc where it can be linked, gated and scoped like anything else.

The active ship is a ship quid in git config as `nosedive-current-ship`, set by
`helm`. A bridge steers one ship at a time, and every command is scoped to the
active ship's decks. `helm` hard-fails while a dive is active: land, pack or
bail first.

Two ships may scope the same repo. This is deliberate. The workspace is mutable,
and jumping a dive after helming rehydrates each repo to whatever pin the new
deck needs.

## Deck

A deck is a bounded scope or domain -- a ticket board, a deployed environment, a
system under a team's purview. It is not inherently a pipeline stage. A team
running shapeup may well name decks `framing`, `shaping`, `building`, `testing`
and set `kind: stage` on them, but stage is not an internal concept: kind may
filter, never reject, so nothing in nosedive reads it.

A deck contains feats, optionally declares gates, and has scopes.

### Deck scopes are declared

A deck's `scopes:` are written, not derived from the feats it happens to hold.
Derivation was a level 2 shortcut and it breaks under decks: a deck that has
just dropped its last feat would derive an empty scope set, leaving a free dive
recorded there with nothing hydrated. Maintained with `add-scope.deck` and
`remove-scope.deck`.

### Read-only by default

There is no scope `mode`. Every scope is read-only until a dive says otherwise,
and a reference repo carries a `note` explaining why it is in scope at all.

Writes happen only through a dive, and only where that dive's scope names a
`work-branch`. Landing commits into a scoped repo with no work-branch is a
failure: either the commits come off that head, or a work-branch is defined.
`--upscope` sets a default work branch and tells the agent to check the repo doc
for `meta.branch-convention` before committing. Nothing enforces that
convention; a team that needs it enforced writes a gate.

## Feats

The deck holds membership. A deck links its top-level feats with a predicate
naming a section: `current.feat`, `future.feat`, `injected.feat`.

A feat never names its deck. A reciprocal feat-to-deck link is a scope leak, and
it is unnecessary: given a feat quid, the deck hosting it is found by searching
the bridge for a forward link to that quid. Tracing needs no backlink and no
reverse scan.

A sub-feat carries `part-of.feat` at its parent, and only when that parent is a
feat -- never at a deck. The chain runs up to a top-level feat, and a deck
forward-links that feat.

Every feat must therefore trace to a deck. The bridge pre-push hook rejects any
that does not.

Orphaning a feat is possible but deliberate, and it costs provenance. Somebody
tracing a feat quid out of a commit in an implementation repo should be able to
learn how the authoring bridge now regards that work; if no deck hosts it, they
are left doing git archaeology on the bridge. Whether something is still
supported must be inferable from the deck hosting it. Removing a feat from the
final deck by hand trips the pre-push hook and takes `--no-verify` -- a recorded
decision to leave the tool's domain management.

### Rendering

A feat carries relations with predicates such as `depends-on.feat`. Link
`meta.structural: true` promotes a relation to a subtree node: it renders
indented, with its gist, exactly as a parent feat renders one level shallower,
and a feat may carry any number of them. Non-structural relations render at the
bottom of the entry as space-indented continuation lines grouped by predicate,
with no bullet of their own.

Traversal keeps a visited set and first-seen qualifier wins, the same rule
`collectLandGates` (`src/lib/landGates.ts:96-145`) already applies to duplicate
gate edges. Cycles are legal under a graph and must not throw.

## Gates

**Every gate rel qualifier names the command that runs it.** `test` runs
`test.gate`, `land` runs `land.gate`, `drop` runs `drop.gate`, `lift` runs
`lift.gate`. A qualifier no command runs is not a gate rel. This is why there is
no `failing.gate` and no verb argument on `test`.

A gate doc never names its own phase. The link does, and carries the
`gate-height` and `test-is-flaky` attributes. One prover serving as both a
`test.gate` on a dive and a `land.gate` on a repo is the ordinary case.

A gate is a gate because a `.gate` rel names it and `meta.test-script` resolves
to a runnable file. There is no kind allowlist.

### Placement

- A **repo** may declare `land.gate` and nothing else. A repo cannot regress in
  the absence of a feat -- what shipped is functionality, not a repository -- so a
  `test.gate` on a repo has no meaning and is rejected in the pre-push hook.
- A **test.gate** must be declared somewhere with a feat in context: a feat
  itself, or a dive or memo carrying `meta.feat`. This is what guarantees a
  failing test gate always has a feat to hang minted work on.
- Deck gates are exit gates: `drop.gate` on a deck is what that deck demands
  before it lets a feat go. A future link meta may let a receiving deck hook an
  arrival.

### A failing gate becomes work

A gate that fails is attached to the dive being worked as `test.gate`, so the
pilot can iterate on it directly with `nosedive test`. Its original declaration
is never rewritten, so the gate still runs in its own phase from its own home.

With no active dive, a failing `test.gate` mints one: `rel: planned.dive` on the
feat that owns the gate, recorded through `record.dive --feat` so it inherits
the managed name, the feat's scopes and a brief. Only `test.gate` failures mint.
A `land.gate` failure cannot, because `land` runs inside an active dive and
requires a feat, so there is always a dive already there.

Dedup is on the doc being linked, not on a qualifier: if any non-bailed dive
already links that gate, somebody is on it.

### Readiness is gate-enforced, not declared

"This feat is not ready to drop because it has not filled in its expectations"
is a `drop.gate` whose script reads the feat and fails. There is no separate
declarative needs-language; a second mechanism for the same thing is not built.

A deck declaring no `drop.gate` at all refuses to drop. The call to action is
the point -- even a deliberate no-op gate is a recorded decision about what that
deck demands.

Likewise, whether a dive must carry test gates before it lands is team policy,
not core policy: a docs-only dive reasonably carries none, and only the team's
own script knows the difference. Refuse-versus-warn needs no new mechanism
either, because `test-is-flaky: true` already reports a non-zero exit as a
warning instead of blocking.

## Commands

- `helm <ship>` -- set the active ship in git config.
- `swab --deck <ref>` -- rerender a deck body from its links. Supersedes
  `update-backlog`. Considers only `.feat` links and ignores every other rel,
  because a deck routinely carries minted `planned.dive` links.
- `record.feat <words...> [--on <deck-or-feat>] [--qualifier <q>]` -- positional
  words are the gist; a leading `<word>:` sets `kind`, so `record.feat idea: do
  thing` yields `kind: idea`. Writes `<q>.feat` on the target, and a
  `part-of.feat` backlink on the new feat only when `--on` names a feat. With no
  `--on` the target is the active ship's `meta.decks[0]`. The qualifier defaults
  to the target deck's `meta.new-feat-qualifier`, or `new`. Supersedes `pitch`.
- `record.deck <words...> [--before <ref> | --after <ref>]` -- adds a deck to the
  active ship's `meta.decks`. The placement flags are one-of; neither appends.
- `drop <feat>` -- resolves a single top-level feat, runs the `drop.gate` links
  its deck declares, and on a clean run moves the feat's link to the next deck,
  commits without pushing, and reports what changed including the commit sha so
  an agent can audit it. Only top-level feats drop -- a sub-feat rides its
  parent. There is no dropping off the end: a feat leaves support by advancing
  onto a deck built for that, so it never stops being findable.
- `lift <feat>` -- the reverse.
- `test [--full]` -- runs `test.gate`. With no active dive it walks the active
  ship's decks as a regression pass; with one it runs the dive's own gates, and
  `--full` widens to the whole walk.
- `land` -- unchanged in requiring an active dive, which is what lets it attach
  failed gates to that dive.

## Migrating from level 2

- `backlog: <quid>` becomes a ship holding that memo as its entry deck. The ship
  name derives from the bridge repo root directory name.
- `child.feat` becomes the deck-held membership described above; `parent.feat`
  becomes `part-of.feat` and stays pure relation.
- Scope `mode: rw` becomes `work-branch: <work-branch-prefix><feat-slug>`, the
  string `land` already computes. `mode: ro` is dropped, since read-only is now
  the default. This rewrites every dive doc in every bridge, and is accepted:
  `ro`/`rw` do not carry enough information on their own, and are redundant once
  a work-branch is present.

## Deliberately not in the model

- **Team and org.** A bridge is a team's meta-repo, so bridge is team. Anything
  beyond that is multi-tenancy and is not level 3.
- **Deck neighbour links.** See Ship.
- **A `mode` on scopes.** See Deck.
- **Recorded gate verdicts.** A gate wanting to know whether a dive tested clean
  should run the tests, not read a claim about them. A stored pass is the exact
  thing that goes stale and lies.

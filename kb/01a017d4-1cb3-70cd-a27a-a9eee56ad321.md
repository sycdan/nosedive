# How do I rebase my pull request onto trunk and publish it?

Your feat's work branch carries commits from dives that have already landed.
Trunk has since moved and now conflicts with them, so the pull request cannot
merge until the branch is rebased -- which rewrites commits that are already
published.

Do not repin or re-jump the dives that landed those commits. Their pins record
the bases they actually built on, and that is history, not bookkeeping. The
rebase belongs to a **new dive** that owns the recovery.

## The sequence

Record a dive on the same feat, then pin it at the head of the work branch --
not at trunk, which is the thing you are rebasing onto:

```bash
nosedive record.dive --feat <feat-ref> --title "Rebase onto trunk"
nosedive record.dive --ref <dive> --repin
nosedive jump <dive>
```

`--repin` with no value already prefers the feat's work branch over trunk, so it
lands on the branch head on its own. If the dive scopes several repos and you
need to move just one, name it: `--repin <ref> --scope <repo>`.

Rebase in the hydrated worktree with git. Nosedive does not do this for you, and
should not -- conflict resolution is yours:

```bash
git -C <workspace-repo> fetch origin
git -C <workspace-repo> rebase origin/main
```

Resolve each conflict, `git add` the result, and `git rebase --continue` until
it finishes. Then publish:

```bash
nosedive land --hard
```

## Why `--hard`, and what it protects

The rebased head is no longer a descendant of what is on the remote, so an
ordinary `land` is rejected -- correctly, because that rejection is the only
thing standing between you and someone else's work.

`--hard` pushes under a lease whose expected value is **this dive's own pin**:
the branch head you started from. It replaces the branch only if the remote is
still exactly there. If anyone pushed to it while you were resolving conflicts,
the push is refused and nothing changes -- not the remote, not the dive, not
your workspace marker.

Ordinary lands are unaffected, and no path in `land` ever force-pushes
unconditionally.

## If the lease refuses

You will see that the branch moved since the dive was pinned. Somebody pushed
while you were resolving conflicts, and your rebase was built on a head that is
no longer current. Take the new head and redo the rebase on top of it:

```bash
nosedive record.dive --ref <dive> --repin
git -C <workspace-repo> fetch origin
git -C <workspace-repo> reset --hard origin/<work-branch>
git -C <workspace-repo> rebase origin/main
nosedive land --hard
```

Note the `git reset --hard` rather than a second `nosedive jump`. Jumping
refuses here, and is right to: your worktree is sitting on rebased commits that
no ref contains, and jump will not move a worktree off work that exists nowhere
else. In this one case the refusal is over-cautious, because those commits are a
rewrite of work that already landed -- discarding them loses nothing that is not
still on the remote.

That is only true while the recovery dive has added no changes of its own. If
you also committed new work here, do not reset: rebase just your own commits
onto the new head with `git rebase --onto origin/<work-branch> <your-old-base>`,
or `nosedive pack` the dive first so the work is captured as patches before
anything moves.

Do not reach for `git push --force`. The lease refused precisely because
something arrived that your rebase never saw, and forcing past it deletes that
work from the branch.

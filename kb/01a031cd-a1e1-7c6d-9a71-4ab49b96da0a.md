# Quickstart

## Your first gate

_nosedive_ is about more than pushing branches. Gates are: you say once what
done looks like, and the tool refuses to publish work that does not meet it.

```sh
nosedive record.gate --gist "A goodbye note sits beside the hello note" \
  --feat add-a-hello-note --name goodbye-note-exists

nosedive test                       # no dive in flight: sweeps the backlog,
                                    # finds the new gate red, and mints a
                                    # dive to fix it

nosedive jump                       # only one dive, no need to specify

nosedive land                       # refuses because the gate is still red

# write the check in kb/artifacts/<gate-id>.mjs

nosedive test --full                # red for the reason the gate checks

# add goodbye.md in workspace/__self and commit there

nosedive test --full                # green
nosedive land                       # pushes work/add-a-hello-note
```

A freshly minted gate fails on purpose, so you know it needs attention.

The dive minted by `test` is in service of that one gate and nothing else, so it
cannot land until the gate is green. Your gate script gets `ctx.repos`, keyed by
repo name, so it can look at the same worktree you are working in --
`ctx.repos.BASE` refers to bridge repo itself.

Important practical note: the gated repo is a hydrated worktree, not the bridge root.
In the gate script, use the repo entry's `root` value resolved relative to
`ctx.bridgeRoot`; e.g. `path.resolve(ctx.bridgeRoot, ctx.repos["your-notes-repo"].root)`.
If you skip that resolution and read from the bridge root directly, the gate will
fail with a misleading "no repo data available" error.

Also remember to commit the edited repo before `nosedive land`: a green gate is
not enough if the scoped worktree still has uncommitted changes.

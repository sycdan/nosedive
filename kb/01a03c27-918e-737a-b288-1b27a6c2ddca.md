# Generated README surfaces

Several blocks in `README.md` are generated by scripts, not hand-written:

`scripts/update-readme-command-surface.mjs` writes both of these, in one pass:

- the levels block, `<!-- BEGIN nosedive-levels -->`, rendered from the
  `kind: level` docs in `kb/`. It also enforces that levels are contiguous from
  0 and that their ids sort in level order.
- the command surface, `<!-- BEGIN nosedive-command-surface -->`, rendered from
  every `kind: command` doc.

`scripts/update-readme-faq.mjs` writes:

- the FAQ, `<!-- BEGIN nosedive-faq -->`, rendered from the `kind: faq` docs.

The scripts can take `--check`, which renders and compares instead of writing,
exposed as `npm run check:command-surface` and `npm run check:faq-surface`. The
command-surface `--check` covers the levels block too.

## Who regenerates them

CI and publish, in the runner, right after `npm ci`. Nothing local does.

The local pre-push hook used to regenerate both and refuse a push whose
committed README was stale, and `prebuild` used to run both `--check` scripts so
an ordinary `npm run build` failed the same way. Both are gone. A generated
surface is a release artifact, and preparing a release artifact is not work every
push has to do.

## What the pipeline step actually checks

Both workflows run the same four commands in order: run both generators, then
run both `--check` modes on top of what was just written.

That ordering is the whole point, and it is not the obvious one. `--check` here
compares the generator's output against a file the same generator wrote seconds
earlier, so it is asserting that **generation is deterministic** -- a second
render disagreeing with the first is a bug in a generator. It is deliberately
*not* comparing against what the branch carries. A pull request whose README
differs from the runner's regenerated README is normal and passes.

Running the generators at all is the other half. Between them they parse every
`kind: command`, `kind: level`, and `kind: faq` document in `kb/`, so a
malformed, missing, or mis-keyed doc makes them throw -- as does a levels
sequence with a hole in it. Once `prebuild` stopped calling `--check`, the
pipeline step became the only thing that parses those documents on a pull
request.

## What the step does not buy

It is tempting to say the step means "code and command-document changes are
tested against the output they actually produce". That is not true, and it is
worth writing down before someone builds on it.

Nothing under `src/` or `scripts/` reads this repository's own `README.md`. The
test suite asserts on the surface stamp in a seeded `AGENTS.md` and on fixture
READMEs written into temporary bridges; the packed-bin gate does the same. No
build step and no test consumes the real file.

So the step's *position* -- before format check, build, and test -- carries no
weight. It sits there because that is where a reader expects setup to sit, not
because anything downstream depends on it. Move it, and every check still means
exactly what it meant. What matters is only that it runs.

## The drift this leaves open

Because nothing local regenerates, `README.md` on `main` drifts from what the
level, command, and FAQ documents render. That is what visitors see on GitHub.

The published package does not drift: `publish.yml` regenerates before it packs,
so the tarball always carries a current README. The gap is the repository's own
copy, and it closes when publish becomes the sole writer that commits its
regenerated output back to `main`.

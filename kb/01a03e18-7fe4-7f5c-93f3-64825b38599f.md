# The publish transaction

Every push to `main` publishes a dev build. There is no path filter on the
trigger, and there is no second place a version is decided. This memo is why.

## Two versions, one of them derived

`scripts/version.mjs` prints both:

- `node scripts/version.mjs` samples the clock and prints
  `yyyy.m.d-<utc millis>`. This is the dev version, and every push to main gets
  a fresh one.
- `node scripts/version.mjs --release` prints `yyyy.m.d` by removing the
  timestamp from a dev version -- from `package.json` by default, or from
  `--from <version>`. It never reads a clock.

The second one is the whole reason `--release` was ever more than a formatting
change. A stable release is a promotion of one dev build that already exists on
npm, so its date has to be that build's date. Sampling a clock instead would
give the promotion its own date, and a build made, tested and published on the
25th would ship as the 26th release whenever the promotion crossed UTC
midnight -- and a rerun of that promotion would name a third date again.

## What main carries

`package.json` on `main` always carries the last **dev** version that was
actually published. A stable version exists in npm and in the runner that
published it, and is never committed.

That is what makes the trigger unfiltered. If a push could reach main without
being finalized, `package.json` would name a release that never happened, and
the recovery below would have nothing dependable to read.

## The finalization commit

A push names a commit. That commit is the release candidate for the whole run,
including any rerun of it, and it is the only thing the run trusts about its own
identity. The candidate is finalized by exactly one managed commit on top of it,
made by `scripts/finalize-publish.mjs`:

- subject `publish(nosedive@<version>): README surfaces updated` or
  `... unchanged`. That is for whoever reads `git log`. It decides nothing.
- trailers `Nosedive-Publish-Source: <candidate sha>` and
  `Nosedive-Publish-Version: <version>`. These are the machine-readable part.
- a diff confined to `README.md`, `package.json` and `package-lock.json`.

The confinement is the point of the script. It runs after the surface generators
and `npm version` have rewritten the tree, so anything else that moved was moved
by a build step editing tracked source. That would ship under a version nobody
reviewed and leave main carrying a change no pull request made, so the release
fails instead. For the same reason the pipeline runs `format:check` and never
`format`: a publish that repaired formatting would ship source no review saw.

The push is a plain `git push`, so main can only fast-forward from the
candidate, and it is authenticated with `GITHUB_TOKEN`, which by design starts
no further workflow run. Those two facts together are what let the trigger stay
unfiltered without looping on its own commit.

## Finishing an interrupted publish

A publish is two writes that cannot be made atomic: a push to `main`, then an
upload to npm. A rerun therefore has to work out how far the last attempt got.
It does that from the candidate sha, the current `main`, and npm -- never from
`github.run_attempt`, which reports that this is attempt two and nothing about
which of the three states it woke up in.

`scripts/decide-publish-recovery.mjs` answers with one of:

- **rerun** -- main is still the candidate, so no managed push survived and the
  whole finalization runs from the start.
- **resume** -- main is a valid finalization naming this candidate, so an
  earlier attempt already stamped and pushed a version. Publish that version;
  mint nothing.
- **superseded** -- main is anything else. A newer head owns finalization, and
  this run exits without publishing.

Validity is `scripts/check-publish-finalization.mjs` and nothing else: parent is
the candidate, both trailers present and well formed, both package files
carrying the trailer's version, changed paths inside the allowlist, and both
README generators leaving the tree unchanged. What `finalize-publish.mjs` writes
is exactly what that check reads back, which is what lets a rerun recognize its
own work.

A resumed run does not re-run the gates. The finalization commit is only made
after they pass, so its existence on main is the record that they did; a rerun
that gated the same tree again would spend minutes to learn what the commit
already says.

npm is idempotent by asking. If the version is already there, the upload is
skipped rather than retried, because npm refuses a duplicate version and a
retried upload would fail a run whose package is already live.

## Promoting to stable

`workflow_dispatch` on `main` promotes one finalization.
`scripts/decide-stable-release.mjs` validates that the dispatched commit is a
managed finalization -- the same check, run against the commit's own parent,
since a finalization sits directly on the source it names -- and derives
`yyyy.m.d` from the version trailer. The dev build must already be on npm;
promoting something nobody can install is not a release.

An existing `v<yyyy.m.d>` tag records which candidate already owns that date. On
this candidate it means a rerun, which repairs whatever is missing. On any other
it is a refusal: a different dev build already shipped as that release, and
replacing it would rewrite what people have installed.

The tag and the GitHub release point at the timestamped finalization commit, not
at the stable version, because that commit is the tree that was built and
tested. The stable version only ever existed in npm and in the runner.

A rerun of an Actions run keeps its original event, so a rerun of a push stays
on the dev path and a rerun of a dispatch stays on the stable path. Neither
needs to know it is a rerun.

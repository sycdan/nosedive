# Explanations live in kb, not in a comment block

When a decision needs more than a couple of sentences to justify, write the
explanation as a `kind: memo` in `kb/` and point at it from the code:

```js
// @see kb/01a03e18-7fe4-7f5c-93f3-64825b38599f.md
```

The form is a bare `@see` and a repo-root `kb/<uuid>.md` path, optionally with a
heading anchor. It works in a `//` comment, a `/** */` block, a shell `#`
comment, and a YAML comment, which is most of what this repo is written in.

## Why not just write the comment

The same decision usually has to be explained in more than one place. The
generated README surfaces are regenerated by two pipelines and deliberately not
by the pre-push hook, so the reasoning belonged in three files; the publish
transaction touches a workflow and four scripts. Copying a paragraph into each
of them means every later correction has to find all the copies, and the ones it
misses become confidently wrong comments -- which are worse than none, because
people believe them.

A memo also outlives the code it explains. A file gets renamed, split, or
rewritten; the memo keeps its uuid, and every pointer still resolves.

## What stays in the source

Short reasons stay where they are. A one-line comment saying why a check is
`<=` and not `<` does not want a document, and turning it into one makes the
reader open a second file to learn something they could have read in place.

The test is length and reach: more than a few sentences, or true in more than
one file, means it goes in `kb/`.

## What the memo owes the reader

A memo reached by `@see` is read by someone who is looking at a specific line
and wants to know why it is that way. Answer that first. Documenting what the
code plainly does, restating the brief, or recording the order things were
built in are all ways of making the reader hunt for the one sentence they came
for.

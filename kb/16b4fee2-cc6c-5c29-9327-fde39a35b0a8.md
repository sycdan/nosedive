# Add repo to feat

Resolves `<repo-id-or-name>` against bridge KB `kind: repo` docs by `id` or
exact `name`, then appends that repo to the active `kind: feat` doc's `scopes:`
list.

The active feat is the one named by the active dive, and nothing else: the
workspace marker `workspace/.nosedive-ref` names a dive, and that dive's
`meta.feat` names the feat. With no dive selected the command fails rather than
guessing. There is deliberately no per-developer "current feat" setting --
selecting a dive is how a pilot says what they are working on, and a second
source could disagree with it.

- `--ref` pins the feat scope to a ref. When omitted, the scope has no `ref`
  key and downstream scope resolution falls back to the repo's configured trunk.
- `--work-branch` records the branch this feat's dives publish that repo to.
  Dives created under the feat inherit it, and `land` pushes there. Without it
  the scope is read-only, which is what a scope naming no branch means: work in
  that repo has nowhere to go until a dive names a branch with
  `record.dive --upscope`.

`mode: ro` and `mode: rw` are never written. A branch says where work goes and
its absence says there is nowhere, so neither key carried anything a scope does
not already state.

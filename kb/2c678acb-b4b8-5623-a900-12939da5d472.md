# Record a gate

Every value is a named flag, and the one optional positional names the gate to
patch -- the same grammar as
[record.feat](fb3d90e6-9dbf-5f1c-9919-6653d12fe085.md), which describes how the
positional is read and what happens to one that names no document. Without it,
`--gist` and exactly one of `--feat` or `--repo` are required and a gate is
minted; with it, only the flags given are applied. `--feat` and `--repo` are
mutually exclusive.

## The doc and the script are one thing

`record.gate` writes both: a `kind: gate` doc carrying
`meta.test-script`, and the script it names at `kb/artifacts/<gate-id>.mjs`.

Minting only the doc would produce something that hard-fails the moment
anything selects it. A gate whose `meta.test-script` is missing or resolves to
no file is a hard error rather than a skip, deliberately -- silently skipping a
broken gate turns it into a passing land -- so the two are never written apart.

The stub fails. It writes its own id to stderr and returns `false`, which the
gate runner reports as exit 1. An unwritten gate that returned cleanly would
report green having checked nothing, which is the failure the whole area exists
to prevent, so an unwritten gate is a red one and the pilot is told where to
write it.

## What it links

A `rel: test.gate` link on the `--feat` target by default, or `rel: land.gate`
with `--action land`. `--repo` declares `land.gate` and implies `--action land`.
An explicit `--action test` with `--repo` is refused: a repo cannot regress
without a feat in context, so a failing repo-declared `test.gate` would have no
document to mint work against.

`--repo` accepts the same repo grammar as `record.dive --upscope`: repo name,
quid, kb path, `.nosedive-ref`, or a directory holding one.

`--height` sets `gate-height`, `--flaky` sets `test-is-flaky`, and `--note` sets
a human-readable `note`, all on that link rather than on the gate doc: one
prover can be a `test.gate` on a feat and a `land.gate` on a repo, and its
attributes differ per declaration. A gate doc never names its own phase.

A `test.gate` is the loop a pilot runs while working -- `land` never collects
it, so it can fail without blocking publication. A `land.gate` is what
publication is conditional on: `land` collects `rel: land.gate` links and
refuses to land while one fails. `--action` defaults to `test`.

`--feat` must resolve to a `kind: feat` doc. A `test.gate` that fails a backlog
sweep -- `test` with no dive on deck -- mints work against the feat that
declared it, so a gate declared anywhere else leaves that failure with nowhere
to go. A gate that fails with a dive on deck attaches itself to that dive
instead, whichever verb was running.

`--name` is the gate's slug in kebab-case, and is what gate reports call it.
Omitted, the gate is named `new-gate-<yyyy>-<mm>-<dd>-<hhmmss>`, so a gate can
be minted before it has a good name and renamed later -- the same default, for
the same reason, as a recorded feat.

## Patching a gate

`--gist` and `--name` are the doc's; `--feat`, `--repo`, `--action`, `--height`,
`--flaky` and `--note` are the declaring link's, and a patch rewrites that link
in place rather than adding a second one. Link attributes this command knows
nothing about survive the rewrite: somebody wrote them, and a height change is
no reason to drop them.

`--feat` or `--repo` on a patch moves the declaration, removing the old
declaring doc's link. Changing a link attribute on a gate no feat or repo
declares is refused -- there is nowhere to put it -- and either flag fixes that.

`--no-flaky` clears `test-is-flaky`. It exists because `--flaky` alone would
make flakiness a one-way door.

`--no-note` likewise clears `note`. A note is documentation for the next human
to open the declaring doc; no command interprets it.

A rename carries into the doc's title heading only where that heading is still
the generated one.

A patch names a gate by its script, not by its `kind`. `test` and `land` both
select a gate through a `.gate` rel and a script that resolves, so a document of
any kind a feat declares that way is one, and a document that resolves no script
is not -- the same rule, so the command that publishes a gate reaches every gate
those two can run.

A patch that sets no field publishes the gate as it stands, doc and script
both. That is the form to reach for once the check has been written into the
stub: nothing else stages that file, and every other command stashes it out of
the way rather than publishing it. A run with nothing left to commit says so
and exits cleanly.

## Scopes

A feat-declared gate writes no `scopes:` key at all. An absent one inherits the
feat's scopes, which is what that gate wants; an explicit `scopes: []` says the
opposite -- this gate needs no repo -- and would pin it to nothing.

A repo-declared gate writes `scopes:` with the repo's bare id. Repo docs do not
normally carry scopes to inherit, and without the gate's own entry `ctx.repos`
would be empty under `nosedive test`. The bare entry names no branch and gate
hydration forces it read-only.

## What it commits

The gate doc, its script, and the feat or repo that declares it, as one commit
with the subject `gate(<name>): created`. The script matters as much as the doc:
a gate whose script never left the machine that minted it resolves to nothing,
and a gate that resolves no script is a hard failure rather than a skip. A
patch commits under `gate(<name>): updated`, carrying the script as well as the
doc, and both declaring docs when the declaration moved. The script is on the
patch path for the same reason it is on the create path: a gate whose script is
not what was published is a gate whose result means nothing. Same rules as
[record.feat](fb3d90e6-9dbf-5f1c-9919-6653d12fe085.md) -- pathspec, no push.

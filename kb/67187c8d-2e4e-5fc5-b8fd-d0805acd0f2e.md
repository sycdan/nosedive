# Preflight

Agents call this before their first reply to the pilot in a session.

## Pre-push hook

Searches upward for the nearest bridge config and reconciles the pre-push hook
of that bridge's Git common directory. Every run re-pins it, so a hook written
by an older nosedive can never go stale.

The installed file is an LF-only executable shim: `#!/bin/sh`,
`# nosedive-managed`, and an invocation pinned to the exact package that ran
preflight. A released package writes
`exec npx -y nosedive@<version> _pre-push.hook "$@"`; a local development
checkout writes its own `node .../dist/cli.js` invocation. It never relies on
an ambient `npx nosedive` version. The gate the shim calls is
[`_pre-push.hook`](9e3a676a-6d2f-5b93-93af-f4608ed28843.md).

### Where it goes

Preflight owns `.git/nosedive-hooks/` and points `core.hooksPath` at it --
always, not only when some other hooks path is already configured.

Claiming the hooks path takes nothing away from the pilot:

- the managed hook runs the bridge's own pre-push first, if any, and that hook's
  exit status is the push's answer -- a gate that says no is not asked twice
- ref updates arrive on stdin, which can only be consumed once, so the managed
  hook reads them and replays the same list into both
- every other hook name present in the pilot's directory is re-exported from
  `.git/nosedive-hooks/`, so claiming `core.hooksPath` switches nothing else
  off. Hooks added after the takeover are picked up by the next preflight
- the directory the hooks came from is recorded in
  `.git/nosedive-hooks/original-hooks-dir`, so later runs still know what to
  chain once `core.hooksPath` names nosedive's own directory

### What preflight will not touch

- A hook the pilot wrote is never rewritten -- only run.
- A foreign hook, or a hook under `core.hooksPath`, that already invokes
  `_pre-push.hook` -- under any launcher, e.g. an aliased `nosedive`, a pinned
  `npx -y nosedive@<version>`, or `node dist/cli.js` -- is left unchanged and
  preflight continues silently. Wrapping it would run the gate twice.

A managed hook outside the active hooks directory is removed rather than left
behind -- including the `.git/hooks/pre-push` that earlier versions installed,
which is how an existing bridge migrates. Git reads exactly one hooks
directory, so a managed hook outside it never runs and nothing refreshes it.
Preflight writes one back as soon as it is the reachable one again.

Config migrations are handled by [`seed`](34c8e9fb-9629-5767-9a81-914f78c63b68.md);
agent instruction files are expected to be source-controlled files.

## Bridge freshness

Once the hook is reconciled, preflight fetches the bridge's trunk before
reading any kb or backlog docs. If the bridge has a remote, preflight prefers
`origin` and otherwise uses the first configured remote, resolves that remote's
default branch from remote HEAD, and fetches that branch into `FETCH_HEAD`.

Preflight never rebases by itself. Instead, it compares the local bridge `HEAD`
to `FETCH_HEAD`:

- If `HEAD..FETCH_HEAD` is empty, the local bridge already contains fetched
  trunk. The bridge status says whether `HEAD` matches trunk or is ahead of it,
  and preflight can exit 0.
- If `HEAD..FETCH_HEAD` is non-empty, the local bridge is missing trunk commits
  and any kb/backlog report from the local worktree may be stale. The bridge
  status says whether `HEAD` is behind or diverged, prints
  `nose: fix this^ first, by rebasing the bridge onto FETCH_HEAD before trusting the backlog below`,
  still prints the rest of the report for context, and exits 1.

A bridge with no remote is still reportable. If trunk resolution or fetch fails,
preflight exits 1 before printing the report because it cannot establish
freshness.

## Session-start report

Once the hook is reconciled and the bridge has been refreshed, preflight
prints, to stdout:

```
== bridge status ==
nosedive-workspace: <absolute worktree path>/<workspace>
nosedive-compatibility-level: <level>
nosedive-pre-push-hook: wired
nosedive-bridge-freshness: HEAD <sha> has diverged from origin/main <sha> (1 ahead, 1 behind)
nose: fix this^ first, by rebasing the bridge onto FETCH_HEAD before trusting the backlog below
nosedive-current-dive-id: <uuid>
nosedive-current-dive-gist: <dive gist>
nosedive-current-feat: <uuid>

== pilot identification ==
nosedive-pilot-name: <git-config-name>
nosedive-pilot-email: <git-config-email>

== dives ==
Available:
  - [<name>](kb/<id>.md) rel=<rel> needs=name,gist,brief,diver never-jumped local-only - <gist>
Held:
  - [<name>](kb/<id>.md) rel=<rel> diver=<email> needs=brief - <gist>

== open work: current feat backlog ==
<backlog memo body>

<guidance>
```

`nosedive-workspace` is always posix-formatted (forward slashes, even on
Windows). The dive and feat lines are omitted together when
`<nosedive-workspace>/.nosedive-ref` names no active dive; if it does but the dive or its
feat can't be resolved, whatever did resolve is still printed and the reason
goes to stderr. The backlog section behaves the same way: if the bridge has no
resolvable backlog memo, the header still prints, the reason goes to stderr,
and preflight still exits 0.

## Compatibility level

`preflight` is the only place level drift is reported. Every other command is
silent about it: a warning printed when nothing is wrong teaches people to
ignore warnings, and preflight runs once per session, which makes it both the
earliest and the only honest place to say so.

`nosedive-compatibility-level:` names the bridge's level, and says what the
running package's level is whenever the two differ:

- **Behind, with a migration in the gap.** The package cannot read the bridge's
  data. preflight prints the levels in the gap, what each changed, and
  `run nosedive seed --headless`, on stderr, and **exits 1** without the rest of
  the report. Bailing at the first `jump` instead would cost the pilot the work
  of choosing what to work on first. The flag is part of the instruction: bare
  `seed` prompts, so an agent following the advice stalls on a question nobody
  is there to answer, and a migration should keep the values the bridge already
  has rather than re-ask for them.
- **Behind, with no migration in the gap.** Nothing needs migrating; the next
  `seed --headless` bumps the config line. Noted in the report, exit 0.
- **Ahead.** The bridge has been seeded by a newer nosedive than this one.
  Noted in the report, exit 0; see
  [`seed`](34c8e9fb-9629-5767-9a81-914f78c63b68.md), which refuses to write the
  lower level over it.

## Dives

The dives listed are the in-flight work reachable from the bridge's configured
backlog memo, not every `kind: dive` doc in the kb. preflight walks out from the
memo along feat links -- `parent`, `child`, and any rel ending `-effort` or
`.feat` -- and lists only the dives those docs link:

- `planned` and `pending` always: a dive nobody has started is offered even when
  somebody has already put their name on it.
- `working` and `jumped` only when the dive carries no `meta.diver`. That is a
  packed dive -- jumped, then put back down -- and it can be picked up again.
  With a diver set it is somebody's live work, and offering it would be an
  invitation to collide.

The role suffix is optional, so `planned.dive` reads as the same edge as
`planned`, which is what `record.dive` still writes. Every other rel is left
out, `landed` and `bailed` included, along with dives no reachable doc links and
dives under feats the backlog does not reach. A session-start report is what can
be picked up now, not an inventory of everything the kb remembers.

Those are split by whether they can be picked up: `Available` is the dives
tagged `needs-diver`, `Held` is the rest. The split is by pickup-ability rather
than by owner because a dive recorded with `record.dive --free` carries no
`meta.diver` at all, so filing by owner would put every unclaimed dive under
nobody. Given the packed rule above, a `Held` line is always a `planned` or
`pending` dive somebody has claimed but not yet jumped.

Each line links the dive doc rather than restating it -- the path is
ctrl-clickable from a terminal, and the scopes and brief the line leaves out are
one click away. Tags are computed from the file on every run, never stored:

- `needs-name` -- no `name:`, or a name that is still just the dive's own id.
- `needs-gist` -- no `gist:`.
- `needs-brief` -- no `## Brief` section in the body.
- `needs-scopes` -- no scope naming a repo.
- `needs-diver` -- no `meta.diver`. `record.dive` writes `diver: null` rather
  than omitting the key, and a literal null reads as absent.
- `never-jumped` -- the body carries no timestamped section, which `jump`
  appends every run.
- `local-only` -- the doc is uncommitted on the bridge, so no other checkout can
  see it.

With no dives at all, the groups are replaced by a single line naming
`record.dive --free`. preflight never mints a dive itself and never sets
`meta.diver`: claiming is the pilot's decision, and a preflight that minted
would leave `--free` with no caller.

The report ends with guidance for the agent reading it -- help the pilot choose
from the dives and the backlog without choosing for them, claim with
`record.dive --ref <id> --diver <email>`, then fill the dive in together, and
`jump` only when the pilot asks.

Pilot identity is the same fields [`whoami`](a40303c1-1362-523f-b095-49178354f878.md)
prints, from the same source: missing `user.name`/`user.email` in git config
fails preflight (stderr, exit 1) the same way it fails `whoami`.

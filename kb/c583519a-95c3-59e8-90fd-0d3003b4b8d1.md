# Record a dive

Without `--ref`, records a new dive and requires `--feat`. New dives use a
managed `<feat-name>.<uuid-last-6>` name, default their gist to `Working on
<FeatTitle>.`, and name their feat in `meta.feat`.

`--effort` is the old spelling for `--feat` and still works as a compatibility
alias. Supplying both with the same ref is accepted; supplying both with
different refs is refused before anything is written. Either flag writes
`meta.feat`; re-homing a dive that still carried the old `meta.effort` key
removes it, so a dive never names two feats.

The first positional names the dive to patch, the same as every other `record.*`
command. It accepts a same-bridge document UUID, bridge-relative KB path,
`.nosedive-ref` path, or a directory containing that marker. Omitted fields
remain unchanged.

`--ref` is the older spelling of that positional and still works; naming the
dive both ways in one call is refused. Unlike the rest of the family there is no
gist fallback here -- this command never took a gist positionally -- so a
positional that names no document is a mistyped ref and is reported as one.

`--brief` writes a `## Brief` section, on create or on `--ref`, and refuses
when the dive already has one: the brief is what informed everything already
built on that dive, so replacing it would make the record lie. A brief that
turned out wrong is a reason to `bail` and pitch a fresh dive, not to edit.

It is written for the agent that will work the dive, not as a readback of the
pilot's ask -- one small slice, where the code is now, and what has to be true
for the dive to be done.

`--title` replaces the document H1. Omitted scopes keep existing scopes on
update, and on create take the scopes of the nearest feat that has any -- the
named feat first, then its `parent` chain, stopping at the first scoped
ancestor. A create that still finds none says so rather than recording an
unscoped dive in silence. `--clear-scopes` starts from an empty scope list.

## Where a scope lands

A scope names `work-branch: <branch>`, the branch `land` publishes that repo's
HEAD to. **Naming one is the whole of what makes a scope landable**, and a scope
that names none is read-only, because work with nowhere to go is work `land`
must refuse. There is no key that says read-only: `mode: ro` said the same thing
twice and `mode: rw` said something a branch says better, so neither is written
any more and neither decides anything when read.

A dive is created with the branches its feat declares, and with none where the
feat has declared none -- a dive has to be explicit about where it will push. A
feat scope still carrying `mode: rw` counts as having declared: its dives
inherit the generated `<work-branch-prefix><feat-name>`, which is the branch
`land` used to compute for itself, so no feat written before this stops handing
work down. The branch comes from the ancestor that declared the scope, not from
the feat the dive names.

Gaining a feat for the first time inherits the same way. Re-homing a dive that
already had one leaves its branches alone: they may have been chosen by hand,
and the new feat's opinion does not outrank the pilot's.

## Where a new dive starts

Every scope is created pinned, and the pin follows the branch: a scope is
recorded at the head that branch stands at on `origin`, and at the repo's trunk
when origin does not have it. Trunk is the answer for the first dive on a feat,
which has published nothing yet, and for any scope handed down with no branch at
all.

The second dive on a feat is what the rule is for. Its predecessor's `land`
moved the branch past trunk, so a dive pinned at trunk would be born behind the
branch it is going to publish to, with nothing to fast-forward and no way for
`land` to accept it -- for a state nothing the pilot did caused, costing a pack,
a `--repin`, a jump and a second land to undo. Recording at the published head
is what makes the next dive stack on the last.

Branches are read on `origin` and nowhere else, the same rule `--repin` follows
and for the same reason: the managed cache is a bare clone that keeps a local
branch of every name origin once held, and a pin only that machine can reach is
not a pin.

## Editing the scope set

`--upscope <repo-ref>` and `--unscope <repo-ref>` both repeat and can be
combined in one call. `--upscope` adds a repo, or gives an already-scoped one a
branch while keeping the pin it has -- upscoping decides where work goes, never
which commit it started from. A repo the dive was not scoping has no pin to
keep, and is pinned the way a created scope is: the head of the branch it is
joining, on `origin`, and trunk when origin does not have it. `--unscope` drops
a repo, and naming one the dive does not scope is a no-op. Naming one repo in
both is refused.

`--work-branch <branch>` sets the branch for every `--upscope` in the same call,
which is why they compose: repos moving together belong on one branch. It
requires at least one `--upscope`. Without it an upscoped repo takes the branch
its feat declared for that repo, or a generated one when the feat has not said.

`--scope <repo-ref>` is not a scope edit. It names the one scope `--repin <ref>`
moves, and takes the same repo spellings `--upscope` does. It was once the
spelling of `--upscope`; upscoping has one spelling now, so a call that meant to
add a repo says `--upscope`.

`--repin` moves scope refs and changes nothing else -- not the branch, not the
scope set. It requires `--ref`, because a create already resolves a pin for
every scope it writes; there is no pin to move on a dive that does not exist
yet.

With no value it moves every scope. Each one is repinned at the head of the
first branch that answers for it, most specific first: the branch the scope
itself names, then the branch its feat declares for that repo, then the repo's
trunk. Every branch is resolved on `origin` and nowhere else, so the pin is a
commit every other machine can reach. A branch origin does not have is skipped
rather than failing, which is why the first dive on a feat -- whose branch
nobody has pushed yet -- lands on trunk.

`--repin <ref>` moves one scope and requires `--scope <repo-ref>` to say which.
A ref is repo-specific, and a flag that silently applied one repo's branch name
to every scope would be a footgun, so the two only mean anything together:
`--repin <ref>` without `--scope` is refused, and so is `--scope` without
`--repin <ref>`.

`<ref>` may be a dive quid, which resolves to that dive's own pin for the repo
`--scope` names -- how a pilot folds in the dive they were stacked on without
hunting for a hash. It accepts a same-bridge document UUID or a bridge-relative
KB path, never a name, and refuses a document that is not a `kind: dive` or that
scopes no such repo. Anything not UUID-shaped is a git ref, resolved on origin
like every other answer.

Every scope's move is reported as `<repo>: <old> -> <new>` with the source that
answered -- a branch, an explicit ref, or the dive a quid named -- because
retargeting a dive onto a branch somebody else pushed to is not a thing to do
quietly.

It exists because a planned dive goes stale by waiting, and because a stacked
dive's pin is the branch its predecessor published to. Nothing else moves a pin:
`--upscope` deliberately keeps the one it finds, and replacing the scope set to
change a ref drops the branch along with it. Combined with `--upscope` in one
call it runs last, so a repo added in the same breath is pinned like the rest.
`jump` names this flag when it finds a pin behind trunk.

Resolving fetches each scope's managed cache, and that fetch matters as much as
the pin does. `land` pushes to the origin URL rather than to the remote name, so
straight after a land no local ref contains the published head and hydration
reads the worktree as carrying unpublished commits. In a chain of dives sharing
one work branch, run `record.dive --ref <dive> --repin` before `jump` on any
dive that was recorded before its predecessor landed: skip it and the chain
stops. A dive recorded after that landing was pinned at the published head when
it was written, and needs nothing.

A repin edits the document and moves no worktree, so which dive the workspace
happens to be on decides nothing: the dive named by `workspace/.nosedive-ref` is
repinned like any other, and folding trunk into an open dive is a thing a pilot
can do without putting it down first.

What a repin can destroy is a commit the new pin cannot explain. Packed work is
captured as the commits ahead of the pin and replayed onto the pin, so for every
scope with a hydrated worktree the repin refuses on one rule only: HEAD and the
new pin have diverged, and the worktree holds committed work the new pin does
not already contain. A new pin that is an ancestor of HEAD, a new pin that
contains HEAD -- what every repin after a merge looks like -- and a worktree
with nothing ahead of its current pin are all ways of not diverging, and all
pass. A refusal names the repo, HEAD, both pins, the commits that would be
stranded, and `pack` as the way to bank them. A scope with no hydrated worktree
is not checked -- there is no HEAD to compare and nothing to strand.

A merely dirty worktree does not block a repin. Uncommitted changes are captured
against HEAD rather than against the pin, so a pack carries them whichever
commit the pin names.

A repin writes the dive document and stops: no commit, no remote. Publishing it
is the ordinary bridge commit the pilot makes for any kb edit, and it has to
happen before anybody else jumps the dive.

A dive scope still carrying `mode: rw` takes the branch its feat declares for
that repo, the same one a dive created under that feat would inherit. `mode` is
never written back, so the branch is what keeps the promise: a repin is not the
pilot revoking writability, and the scope would otherwise come out read-only.
Where the feat declares no branch for that repo there is nothing to inherit, and
the scope becomes read-only with a line on stderr naming the `--upscope` that
gives it one. A scope that already names a branch keeps it, and one that names
none and never carried `mode: rw` stays read-only.

A pin repinned onto a work branch is often behind trunk on purpose, and `jump`
still reports it as "pinned N commits behind <trunk>". That line is information,
not a defect: it cannot tell a pin left to rot from one chosen deliberately, and
the flag it recommends is this one.

When `--diver` equals the configured Git pilot email, the updated dive becomes
the active workspace dive if no different active dive exists.

`--diver` claims a dive nobody holds. It refuses to reassign a dive that
another diver already holds, because that pilot may be working it right now.

`--takeover` is how a held dive changes hands: it reads the current holder off
the dive, writes the configured Git pilot email in their place, and refuses
when the dive is not held at all. It takes no value and cannot be combined
with `--diver`, so a takeover can only ever assign the dive to the pilot
running it, and lands as its own commit -- the takeover is on the record.

`--packer` puts a dive down: it moves whatever `meta.diver` holds into
`meta.packer` and sets `meta.diver` to null, so the dive is claimable again and
the document still says who released it. Like `--takeover` it takes no value --
the packer is whoever the dive already names as its diver, so accepting one
would only create a way to type it wrong -- and it requires `--ref`.

It refuses a dive nobody holds, a dive held by anyone but the configured Git
pilot email, and a run with no `user.email` configured in the bridge. It also
refuses the dive named by `workspace/.nosedive-ref`, naming `pack`: `pack` is
the one way to put down the dive you are on, because it also clears the marker
and resets the scoped worktrees, which `--packer` knows nothing about.

`pack` and `--packer` are one operation reached two ways -- `pack` releases the
dive it just captured, `--packer` releases one recorded somewhere else. `jump`
clears `meta.packer` when it claims a dive, because a dive somebody holds has no
packer.

`--free` records an empty dive and takes no other option, because every field
it would set belongs to a dive this is not: no feat, so no managed name, gist,
title, brief, meta or links. Its own id stands in as the name, marking it as
still needing one. It scopes every repo the backlog memo covers, always `ro`,
and warns when the backlog covers none rather than refusing. It claims nobody
and never becomes the active workspace dive, and `jump` refuses it while it has
no feat and no brief -- it is somewhere to hang work, not a dive that can be
picked up as it stands.

## What it commits

The dive doc and the feat whose reciprocal link it wrote, plus the feat it was
re-homed away from, as one commit. A create is subject `dive(<name>): created`
and an edit `dive(<name>): updated`, so a repin or an upscope is a commit of its
own rather than something a later `jump` sweeps up. Same rules as [record.feat](fb3d90e6-9dbf-5f1c-9919-6653d12fe085.md) --
pathspec, no push.

`workspace/.nosedive-ref` is not part of it. That marker says which dive this
machine is working, which is nobody else's business.

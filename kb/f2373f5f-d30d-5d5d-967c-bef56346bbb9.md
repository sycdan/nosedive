# Jump

Works on one dive, and takes an optional `<dive-ref>` saying which. With no
argument it works on the dive already on deck. With one it picks that dive up
first -- resolved the same way `record.dive --ref` resolves it, so a UUID, a
`kb/<id>.md` path, a `.nosedive-ref` file, or a directory holding one all name
the same dive.

| invocation | behaviour |
|---|---|
| no argument, a dive on deck | jumps the dive on deck |
| no argument, nothing on deck | prints the dives that could be jumped, exits 1 |
| `<dive-ref>`, nothing on deck | claims that dive and jumps it |
| `<dive-ref>`, the same dive on deck | re-jumps it |
| `<dive-ref>`, a different dive on deck | refused, naming the dive being held |

The dives it offers, and the dives it will accept, are the ones the backlog walk
reaches and nobody else holds -- the same "Available" list `preflight` prints,
from the same rule, so a dive offered at the start of a session is never one the
claim then refuses. With nothing on deck and nothing eligible, `jump` says there
is nothing to pick up and errors with `no-active-dive.error` rather than
printing an empty list. A `<dive-ref>` naming a dive that is not eligible is
refused *with* that list, so the reader never has to run a second command to
find out what they should have named.

Claiming writes the pilot's email to `meta.diver`, writes `.nosedive-ref`, and
rides the commit `jump` already makes. Taking a dive off another pilot is not
this command's job: `record.dive --ref <id> --takeover` still is.

Requires a dive with
a `## Brief` section -- an unbriefed dive errors before anything is hydrated,
naming the `record.dive --ref <id> --brief` call that fixes it. `jump`'s output
is a handoff, and there is nothing to hand over without a brief.

For every repo scoped on that dive, hydrates a worktree detached at the scope's
pinned `ref` (creating it under the managed cache if it doesn't exist yet, same
as `hydrate-repo.workspace`).

### Hydrating over an existing worktree

A worktree that is already there gets `hydrate-repo.workspace`'s rule, not one
of its own:

- Already detached at the pin: left exactly as it is. No checkout runs.
- On some other commit that a local or remote ref reaches: moved to the pin, and
  the run says which commit it moved off. This is the `pack` -> repin -> `jump`
  path -- `pack` leaves the worktree on the old pin and the repin moves the pin
  on, so the commits being stepped over are ones origin already has.
- On a commit no ref contains: refused. Those commits exist nowhere else, and
  moving off them is the one way `jump` could destroy work that was never
  written down.

The refusal names every offending repo in one message -- repo, worktree path,
current `HEAD`, the resolved pin -- and points at
[hydrate-refuses-unpublished-commit](019fcb35-d660-7318-ac4c-3d5aeed3a81e.md)
for the three recourses. It is one message rather than one run per repo because
nothing moves until every scope has been checked: a refusal that has already
relocated three of five worktrees is not a refusal.

A worktree that was just `land`ed reads as unpublished and is refused, which
looks like a bug and is not. `land` pushes to the origin URL rather than the
remote name, so nothing local records that the commits arrived; the fetch inside
`record.dive --ref <dive> --repin` is what makes them readable again. In a
stacked chain of dives on one work branch, run that repin before every `jump`.

### Stale pins

A pin the dive has fallen behind on is reported on stderr, naming how far behind
trunk it is and the `record.dive --ref <id> --repin` that fixes it. A planned
dive goes stale by waiting -- anything that merges while it sits leaves it a
commit further back -- and the agent picking it up was not there when the pin
was chosen, so it has no reason to suspect it. Working from a stale pin is not
silent-in-review, it is silent everywhere: gates prove a tree nobody will merge
into, and overlapping edits surface as conflicts later instead of errors now.

It is a warning and never a refusal. A dive that merely took a while is the
ordinary case, and a pull request three-way merges against the merge base, so a
stale base costs a wrong starting point rather than a damaged trunk.

Only a strict ancestor of trunk counts. A pin ahead of trunk or diverged from it
was chosen deliberately and is left alone. The check adds no network call of its
own -- it reads the refs hydration has already fetched -- so a cache that has
never seen trunk simply reports nothing, and an offline machine still jumps.

It recreates [the dive's scratch space](019feeeb-ff29-720d-ad65-0c77a2957744.md).

Then, for every patch chain the dive links with `rel: patch`, walks it
oldest-to-newest via each memo's `rel: next` and reapplies in order:

- A `<sha12>.<slug>` memo is a real commit: applied with `git am`, so the
  original sha, author, and message survive when the parent tree still
  matches.
- A `dirty.<slug>` or `bridge-wip.<hash>` memo is a working-tree diff: applied
  with `git apply --binary`, left uncommitted.

`<slug>` matches a chain to the scoped repo whose kb `kind: repo` doc has that
`name`; a `bridge-wip.*` chain applies straight onto the bridge's `kb/` tree
instead, and is deliberately left uncommitted -- bridge content changes only
land when a human commits or runs `land`.

## Commit freely, never push

Every hydrated worktree is a sandbox. `jump` (re)installs the managed hooks in
worktree-local config, so they outrank anything tooling writes to the shared
repository config -- npm's `prepare` lifecycle, for one, rewrites
`core.hooksPath` on every `npm ci`; `jump` clears that stale shared value each
run. Commit as often as you like in a writable scope, in small commits, and
react to whatever the hooks tell you.

Pushing is blocked outright: a worktree-local `remote.origin.pushurl` sentinel
fails any push to `origin`, and `--no-verify` does not defeat it because it is
config, not a hook. Fetching still works. Publishing is `land`'s job, from the
bridge, to the branch the feat names -- see `land`.

## Bookkeeping

Each chain applies independently: as soon as one applies cleanly, its memo
docs and `.patch` artifact files are deleted and its `rel: patch` link
removed from the dive doc. A chain that fails partway is left untouched --
memos, artifacts, and its `rel: patch` link all stay on the dive for retry --
and does not stop the remaining chains from being attempted.

`meta.diver` is set to the pilot's email when this run claimed the dive, and the
bridge commits and pushes that state regardless of whether every chain
succeeded -- staging the dive doc and whichever artifact files the successful
chains deleted, same fetch + `merge --ff-only` + push discipline as `pack` -- so
already-applied progress is never lost or re-attempted on retry. If any
chain failed, `jump` reports it and exits non-zero after committing.
`.nosedive-ref` is (re)written last, on success or partial failure alike.

A dive with no `rel: patch` links still hydrates every scoped repo at its
pinned ref; it just has nothing to reapply.

## Jumped section

After hydrating and before the commit it makes, `jump` appends a section to
the dive doc:

    ## jumped <iso timestamp>

    <diver> picked up <feat name>, hydrating <n> scoped repos.

    - repo=<name> path=<worktree path> work-branch=<branch> ref=<resolved commit>

One line per scoped repo, and `work-branch=` only where the scope names one --
a scope says where its work goes by naming a branch, so a read-only scope
carries no branch and the line says nothing rather than saying `ro`.

`ref=` is the commit hydration resolved, never the scope's `ref:` string. A
`ref:` may name a branch, and a branch moves: a section recording the name
records nothing a reader can go back to, while the sha says which tree the dive
was actually picked up on.

The lead line is there because the per-repo lines alone are paths and shas
that never say what event produced them. `<diver>` is `meta.diver`, the dive's
recorded holder, falling back to the rc pilot on a dive nobody has claimed.
When that holder is the pilot running the command, and the bridge's git config
carries a `user.name`, it is written in git's author form:

    Dan Stace <dstace@gmail.com> picked up nosedive-level-2, hydrating 1 scoped repo.

The name is display only. `meta.diver` stays the email, because that is the
identity that compares across checkouts, and only the local git config can
supply a name for it -- so a dive held by another diver, or a pilot with no
`user.name` set, renders the bare email instead.
The scope count is stated because a dive scoping no repo and a run whose
repos all dropped out would otherwise render identically.

The heading is labelled for the same reason `land` writes `## Land report` and
`test` writes `## Test report`: one heading shape across every command that
appends to a dive. It is read back by the one decomposer in
[append-log.dive](f29ec670-caea-5b77-ba51-c7dba1468b0b.md), which finds the
stamp wherever it sits, so the bare-stamp sections older dives carry still
read as progress and nothing needs migrating.

The section is part of the same commit `jump` pushes, so a dive that has ever
been jumped carries the mark on its face -- `never-jumped` is read off the
absence of any timestamped section. A partial patch-chain failure still leaves
a usable, committed workspace, so the section is still appended; only a
failure that aborts the whole run before the commit (an unsafe `meta.patch`, a
missing repo doc, and the like) leaves nothing appended.

## Handoff

On success `jump` ends by directing the agent reading it to the dive doc and
the feat resolved from `meta.feat`, both as paths relative to the cwd
`jump` ran in, then to do the work the brief names and append a timestamped
section saying what it did. It also names [the dive's scratch
space](019feeeb-ff29-720d-ad65-0c77a2957744.md). The brief itself is not to be
edited -- it is the record of what the work was started for.

Nothing is printed after a failed patch chain; a partial workspace is not a
handoff.

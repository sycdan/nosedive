# Record a feat

Every value is a named flag. The one optional positional names the feat to
patch, so the same command records a feat and edits one, and the whole `record`
family reads the same way. Without it, `--gist` is required and a feat is
recorded; with it, only the flags given are applied and everything else stands.

The positional accepts what any document reference does: a feat doc quid, a
bridge-root KB path such as `kb/<id>.md`, a `.nosedive-ref` path, or a directory
holding one. Whether it names a document is decided by asking the bridge, and a
positional that names nothing is read as a gist under the retired spelling --
with a notice on stderr saying so. That fallback is level 2's only; level 3
reads the positional one way.

`--name` is the feat's leaf slug in kebab-case. When it is omitted on a record
the feat gets a timestamped default name, so a feat can be recorded before it
has a good name. On a patch it renames the leaf, and every name built from it
moves too: descendant feats carry the chain, and the dives on all of them carry
managed names. The body's title follows only where it is still the generated
one, because a title somebody wrote is not a slug.

`--parent` accepts a feat doc quid, a bridge-root KB path such as `kb/<id>.md`,
or an exact feat `name`. The feat's `name` is the leaf-first slug chain
`<slug>.<parent-chain>`, and parent and child link to each other in `links:`
with `rel: child` and `rel: parent`. On a patch it re-homes the feat, moving
those links and the whole name chain under it; `--no-parent` makes the feat a
backlog root again. Re-homing keeps the backlog honest: a feat that gains a
parent loses its backlog link, because its parent already reaches it, and one
that loses its parent is injected back.

A recorded doc holds only frontmatter and a title heading. Framing belongs in
the feat's own body once there is something to frame.

## The scope a new feat can work out for itself

A feat that scopes no repo hands every gate declared on it an empty repo set,
so such a gate cannot pass under `nosedive test`, which reads its workspace from
the feat. This command closes that hole where the answer is not a guess: when
the feat has **no parent** and the bridge registers **exactly one** `kind: repo`
doc, the new feat scopes that repo, with the work branch `record.dive --upscope`
would generate for it -- the bridge's `work-branch-prefix` followed by the
feat's name. Naming a branch is what makes a scope writable, so dives recorded
on the feat inherit somewhere to push without being told.

Both conditions matter:

- **No parent.** A parented feat already inherits its parent's scopes, and a
  scope written here would be a second source that can disagree with it.
- **Exactly one repo.** With several registered there is no defensible guess --
  not even the bridge's own repo, since a bridge usually carries several and its
  feats target one that is not the bridge. The feat then writes no `scopes:` key
  at all, and the pilot chooses with `record.dive --upscope`.

A scope chosen this way is reported on stdout, naming the repo and its id, so
the choice is never silent. The suggested `record.dive` line printed afterwards
drops the scoping flags in that case, because they would re-open a settled
question.

## What it commits

The feat doc, the parent it linked, and the backlog memo when it injected one,
as one commit with the subject `feat(<name>): created`. A patch commits the
same way under `feat(<name>): updated`, and carries everything it moved: both
parents when the feat was re-homed, the backlog memo when its link changed, and
every doc a rename renamed.

Nothing else commits a feat. `jump` and `land` stage their own paths and stash
everything else around the push, so a document no command commits lives in one
working tree and reaches no clone of the bridge. It is a pathspec commit, so
whatever the pilot had staged stays staged and unpublished.

It commits and does not push: a network round trip in front of writing a
document is a new way for writing one to fail, and the next `jump` or `land`
carries these commits out with its own.

A bridge that is not a git repository is not refused. The document is written
either way; there is just nowhere to record it.

Recording fails when a feat with the same slug chain already exists, and so
does a rename or a re-home that would land on one.

A patch that sets no field is not one of those failures. It means publish this
document as it stands, which is how a body somebody edited by hand reaches a
clone -- the record family is the only thing that commits these documents, and
until one of them runs there is nothing to publish. A run with nothing left to
commit says so and exits cleanly, so repeating it is safe.

This is the command formerly spelled [pitch](d59ff8d4-3366-54cd-ac2e-7ef869752b3a.md),
under the name of the thing it records. The old spelling still runs and routes
to the same implementation, so nothing pinned to it breaks.
